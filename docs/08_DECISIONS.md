## 2026-09-02 — Backend framework: FastAPI, not Django
**Decision:** FastAPI, SQLAlchemy, Alembic, Celery — same stack as Elevare's existing recruitment platform.
**Why:** Emmanuel has current, recent production FastAPI experience (multiple prior projects) and would need to refresh Django. The recruitment platform already runs FastAPI + SQLAlchemy + Alembic + Celery + asyncpg in production, with real incidents already debugged there (Celery worker OOM, Alembic multiple-heads) — meaning the usual "Django ships faster, batteries included" argument doesn't hold when the alternative isn't a blank slate. Django's admin-panel advantage is also weaker here since the product ships a dedicated React frontend, not Django's HTML admin as product UI (SQLAdmin, built on the same SQLAlchemy models, covers the internal-ops-console use case reasonably well instead). Django's async ORM is also a `sync_to_async` shim over a synchronous driver, not real non-blocking I/O like SQLAlchemy `AsyncSession` + `asyncpg` — a real (if not urgent-for-MVP) difference for later features like cross-platform recruitment integration and concurrent AI calls.
**Impact:** `00_PROJECT_CONTEXT.md` tech stack table updated. Sole backend engineer now maintains one stack across both Elevare products.

## 2026-09-04 — Multi-tenancy: shared schema, shared database, enforced by Row-Level Security
**Decision:** One Postgres database, one set of tables, every table carries a `NOT NULL organization_id`, isolation enforced at two independent layers: application-level authorization (role/permission checks within a tenant) and Postgres Row-Level Security policies (the tenant boundary itself, enforced by the database regardless of what the application queries for).
**Alternatives considered:**
- Schema-per-tenant (separate Postgres schema per customer) — rejected. Migrations run once per schema instead of once total, connection pooling (PgBouncer transaction mode) doesn't play well with per-request `search_path` switching, and cross-tenant analytics get much harder. A worse position on both axes than shared-schema, not a genuine middle ground.
- Database-per-tenant — rejected as the MVP default, kept as a future option. Strongest isolation, but highest operational cost (migrations, backups, and monitoring all multiply per tenant). This is the right answer for a specific enterprise contract that demands dedicated infrastructure (data residency law, noisy-neighbor elimination, independent audit/backup, or simply a procurement requirement), not for every customer by default. Real-world parallel: MongoDB Atlas sells exactly this spectrum as Shared vs. Dedicated cluster tiers.
**Why RLS specifically, not just application-level filtering:** application authorization checks ("is this user allowed to see this resource") remain necessary and are not replaced by RLS — they solve a different problem (in-tenant permissions, e.g. a Manager in one department shouldn't see another department's payroll even though it's the same organization). RLS solves the one thing application code can't be trusted to always get right: a `SELECT` that forgets its `WHERE organization_id = ...` clause, a raw script, a rushed admin tool, a future engineer unfamiliar with the convention. Postgres enforces the tenant boundary as an invisible policy on every query regardless of what the application asked for. This is the standard defense against IDOR-style cross-tenant leaks (Broken Access Control topped OWASP's 2021 Top 10), which is the single most common way multi-tenant SaaS actually gets breached in practice.
**Implementation notes:**
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` plus a policy checking `organization_id = current_setting('app.current_org_id')::uuid` on every tenant-scoped table.
- The current tenant is set once per request via `SET LOCAL app.current_org_id = ...`, inside a transaction, in a single FastAPI dependency, not scattered through the codebase. `SET LOCAL` (not plain `SET`) matters because pooled connections (PgBouncer) are reused across different tenants' requests — a session-scoped setting could otherwise leak between them.
- Elevare's own cross-tenant admin/analytics queries (e.g. billing status across customers) go through a separate, tightly controlled DB role permitted to bypass RLS — not the same connection path application requests use.
**Impact:** `00_PROJECT_CONTEXT.md` tech stack table updated from "leaning" to decided. This is now safe to build against in the database/system design pass.

## 2026-09-04 — Generic Workflow Template/Step model designed, closes the long-standing "Workflow Management" design gap
**Decision:** Workflows (the "Workflow & Departmental Interdependency" MVP feature, §6) are built as a fully generic engine, never as anything specific to Elevare's own process. Elevare's lead-intake process is just the first real data entered into the same tool every customer gets, not a feature built for Elevare specifically.
**Model:** WorkflowTemplate (name + ordered steps) → WorkflowStep (department, default turnaround time, position, optional default assignee) → WorkflowInstance (one running case) → Task (auto-created per active step, inherits deadline, completion triggers the next step). A department can appear more than once in one template. A step's task goes straight to its default assignee if one is set, otherwise lands with that department's manager to delegate. Deadlines are tracked as `due_at` vs `completed_at`; a task open past `due_at` flips to Overdue and notifies before it's even finished, not just after.
**Why this shape, and why it took several passes to land on:** the first drafts conflated things that needed separating, an external tool's data (a CRM) with Workforce OS's own task mechanism, a KPI-measured event (response time, no discrete task needed) with an actual assignable task, and a single hardcoded process with a genuinely reusable engine. Working through Elevare's own recruitment process, then a second, unrelated example (a retail company's complaint-resolution process, different departments, different step count, same engine, no code changes) is what confirmed the model is actually generic and not secretly Elevare-shaped.
**Permission:** template creation/editing is available to HR Administrator (org-wide) or any Manager. A manager building a workflow spanning other departments is expected to have already confirmed realistic turnaround times with those departments, same as they would without any software involved — no formal cross-department approval gate in MVP.
**Status:** Emmanuel proceeded with this model while flagging he doesn't yet have full confidence in every part of it. Revisit and refine once it's visible as an actual schema or screen, rather than treating this as unquestionable.
**Impact:** `01_REQUIREMENTS.md` §6 rewritten with the full model, cross-referenced to §7's weighted KPI scoring (same `due_at`/`completed_at` comparison feeds both).

## 2026-09-07 — Soft-deleting a department/position is blocked, not cascaded, while active references exist
**Decision:** Deleting a department or position fails with a named reason (e.g. "5 active employees still assigned") if it still has active employees, open/in-progress tasks, or a pending AI suggestion attached. No cascading delete, no silent allow.
**Why:** caught in the 2026-09-06 gap review as an undefined rule. Cascading was rejected, it risks quietly wiping or orphaning real employee records. Silently allowing it was rejected too, it would leave active work pointing at something that no longer coherently exists. Blocking with a specific reason is the safer default and doesn't require new cascade machinery.
**What's unaffected:** historical references (a completed task, closed KPI scores) already had this covered by the existing soft-delete convention, nothing changes there.
**Impact:** `01_REQUIREMENTS.md` §2, `04_DATABASE.md` Cluster 2 design notes.

## 2026-09-07 — AI Suggestion generation made idempotent against Celery retries
**Decision:** A partial unique index on `ai_suggestions` (`organization_id`, `suggestion_type`, `position_id`, `department_id`, `kpi_id`, `suggested_department_name`, `WHERE status = 'pending'`), paired with `INSERT ... ON CONFLICT DO NOTHING` in the generation code.
**Why:** caught in the 2026-09-06 gap review. Celery retries failed jobs by default; without this, a retried generation job could create a duplicate pending suggestion for the same target. A database-level constraint was chosen over an application-level check-then-insert because the latter has a race condition under concurrent execution, the database is the only place this guarantee actually holds.
**Impact:** `04_DATABASE.md` Cluster 4, `06_AI_DESIGN.md` new Idempotency section.

## 2026-09-07 — Billing: manual for MVP, Paystack/Flutterwave, automated subscription billing deferred
**Decision:** MVP billing is manual. Elevare invoices a customer directly, they pay via a Paystack or Flutterwave payment link (same providers already assumed for payroll disbursement in `01_REQUIREMENTS.md` §9) or bank transfer, and Elevare staff records it by setting `organizations.subscription_status`/`subscription_expires_at` through the internal admin scripts already designed for the RLS-bypass role. No self-serve checkout, no automated recurring billing, no automated access enforcement based on these fields, all deferred to Phase 2.
**Why:** No SaaS company, regardless of size, builds its own payment processing, PCI compliance and recurring-billing logic (proration, dunning, invoicing) are deep, already-solved problems, always handled through a third-party platform. The open question was timing, not vendor. Most early-stage B2B SaaS companies handle their first cohort of customers manually rather than building automated self-serve billing before there's proven demand for self-serve signup at scale, and this MVP being demoed to investors and pilot customers doesn't change that, a functioning manual process is a normal, expected answer at this stage, not a gap.
**Vendor choice:** Paystack or Flutterwave over Stripe, both are established Nigerian fintechs with real NGN support and existing subscription/recurring-billing APIs for when Phase 2 automation is built; Stripe's direct Nigerian support is inconsistent. Reusing whichever gets picked for payroll disbursement avoids a second third-party integration.
**Impact:** `04_DATABASE.md` Cluster 1, `organizations` gets `subscription_status`/`subscription_expires_at`. Automated billing (self-serve checkout, metering, dunning) logged here as explicit Phase 2 scope, not built now.

**Addendum, same day:** payment history visibility for the customer is a real, separate small addition, not covered by the above. `billing_records` (Cluster 1) is a payment history log, populated manually alongside the fields above, distinct from actual invoice generation, which stays Paystack/Flutterwave's job, not built in-house. `GET /billing/history` (Owner/HR Administrator only) and a matching read-only frontend screen were added for this. ## 2026-09-05 — AI suggestion generation: LLM API call, not a hand-curated rules table (technical implementation choice, does not need Jennifer's sign-off)
**Decision:** Critical-role and revenue-allocation suggestions are generated by calling an LLM (Claude/GPT/Azure OpenAI, provider TBD) with the org's existing department/position/industry context, not by matching against a hand-written table of title patterns per industry.
**Why the original "rules-based" framing needed revisiting:** `01_REQUIREMENTS.md` §8 confirms, as an actual product requirement from Jennifer, "AI suggests, human approves, nothing auto-activates." It does not require any specific implementation technique. "Rules/template-based, not ML" was Emmanuel's own technical framing underneath that requirement, chosen because training a custom ML model needs a proprietary dataset that doesn't exist. That framing missed a third option: calling an already-trained LLM via API needs no dataset at all, and avoids the real practical problem a hand-curated rules table would have created, someone, most likely Jennifer, would have had to author and maintain title-matching patterns for every industry this product might ever sell into. ## 2026-09-17 — Live app DB role fixed: `elevare` (superuser) was being used for real traffic, RLS was never actually enforced
**Decision:** The live app (FastAPI, Celery worker, Celery Beat) now connects as `elevare_app`, a newly-provisioned ordinary Postgres role with no `SUPERUSER`/`BYPASSRLS` attributes (`backend/scripts/db/provision_app_role.sql`). `DATABASE_URL` points at it. **What was actually wrong:** `docker-compose.yml`'s `POSTGRES_USER: elevare` makes `elevare` a Postgres superuser — that part is correct and unavoidable, every fresh Postgres cluster requires exactly one superuser at `initdb` time, regardless of what it's named. Superusers (and any role with `BYPASSRLS`) skip RLS checks entirely, so every RLS policy documented since 2026-09-04 was installed correctly and syntactically fine, but had never actually been enforced against a real application request — for the whole of M1 and the portion of M2 leading up to this fix. Every earlier "proof" RLS was working was actually the app's own `WHERE` clauses happening to filter correctly, not Postgres enforcing anything.
**How it was caught:** a new test (`test_patch_membership_not_found_across_orgs`) returned 200 instead of the expected 404 — cross-org access that should have been invisible under RLS was succeeding. Confirmed via direct `pg_roles`/`pg_tables` queries that the app's own connection had `rolsuper=t`.
**Follow-on bug this exposed:** see next entry — `INSERT ... RETURNING` requires the read (`USING`) policy too, not just `WITH CHECK`. This only started failing once the app stopped running as a role that bypassed the check entirely.
**Impact:** `app/core/config.py` gets `migration_database_url`; `.env`/`.env.example` split `DATABASE_URL`/`MIGRATION_DATABASE_URL`; `alembic/env.py` uses the migration credential. `docs/RLS_POLICIES_EXPLAINED.md` §2 and `07_SECURITY.md`'s new provisioning checklist explain this for future reference. `docker-compose.yml` itself required no change — the fix is which credential each process is handed, not the container topology.

## 2026-09-17 — `INSERT ... RETURNING` needs the read policy satisfied too, not just the write policy
**Decision:** `OrganizationRepository.create_organization` now generates the new org's `id` in Python (`uuid.uuid4()`) before constructing the `Organization` object, and sets `app.current_org_id` to that exact id before the `INSERT` runs — rather than adding a `USING` exception to the `organizations` RLS policy.
**Why:** once the app stopped running as a superuser (previous entry), registration started failing with "new row violates row-level security policy for table organizations" even though `WITH CHECK`'s bootstrap branch should have allowed the insert. Root cause: the ORM's `flush()`/`refresh()` always issues `INSERT ... RETURNING` to read back server-generated columns (`created_at`); Postgres requires a `RETURNING`ed row to also satisfy the table's `USING` (read) policy, not just `WITH CHECK` — confirmed directly via `psql` as `elevare_app` (insert succeeds without `RETURNING`, fails with it). `organizations`' `USING` clause deliberately has no bootstrap exception (giving it one would mean any request that forgets to set org context could read every organization's row) — so establishing the real org context before the insert, rather than relaxing the read policy, closes the gap without reopening that hole.
**Correction to a prior claim:** this fix initially failed a different way — reading `new_organization.id` immediately after `Organization(**organization)` returned `None`/unset. `BaseModel.id`'s Python-side `default=uuid.uuid4` is only invoked at `flush()`, not at object construction, contrary to what had been assumed/stated earlier in this project. Fixed by generating the id explicitly before constructing the object.
**Impact:** `tenancy_identity/repository.py`'s `OrganizationRepository.create_organization`. `docs/RLS_POLICIES_EXPLAINED.md` §8 documents the general `RETURNING`-vs-`USING` mechanism for future tables that hit the same pattern.

## 2026-09-18 — Membership deactivation scoped per-org, and two deeper bugs it uncovered by actually testing the fix
**Decision:** `PATCH /memberships/{id}` with `is_deactivated=True` now sets a new `Membership.deactivated_at` (nullable timestamp), not `User.account_status`. Deactivating someone from one organization no longer locks them out of every organization they belong to — `User.account_status` stays what it was, untouched by this endpoint. `get_current_membership` (`core/dependencies.py`) and `refresh()` now reject a deactivated membership the same way a missing one is rejected. `login()` filters to active (non-deactivated) memberships when picking which org to log into, and re-inviting a previously-deactivated person reactivates their existing row instead of failing on the unique constraint or creating a duplicate.
**Why scoped, not global:** raised as a direct question, confirmed by the user — a person in two unrelated organizations (a consultant invited into a client's org, say) must not have Org A's HR Administrator able to lock them out of Org B. `User.account_status` is deliberately global (2026-09-13's "sole account-state field" decision) for account-level concerns (banned, suspended platform-wide); membership-level access needed its own, separate flag.
**Two real, pre-existing bugs surfaced only by writing a real cross-org test and running it, not by reading the code:**
1. **`login()` never established real org context before relying on eager-loaded organization data.** It only "worked" in the existing test suite because the test environment's shared connection/transaction happened to leave a matching `app.current_org_id` behind from an earlier step (registration) in the same test. On a genuinely fresh connection (production), `organizations`' own RLS policy (no bootstrap-read exception at the time) would have silently returned no organization at all. 2. **`organizations`' RLS policy had no bootstrap-read exception at all**, meaning `GET /me` could never actually return organization details for more than one membership — RLS only ever allows seeing one org's row at a time otherwise. Read-only exception — `WITH CHECK` (writes) is unchanged.
3. **Both `login()` and `get_me()` now explicitly clear `app.current_org_id` before their own bootstrap logic runs**, rather than assuming it was never set. **A new exception, `NoActiveMembershipException` (403), replaces reusing the generic `InternalServerErrorException` (500)** for "this user has zero active memberships anywhere" at login — deactivation makes this a normal, reachable outcome now, not the anomalous edge case (a brand-new user with literally zero memberships ever) the original 500 was written for.

## 2026-09-18 — `GET /memberships` paginated with `paginate()` (offset), not `paginate_cursor()`
**Decision:** `GET /memberships` now takes `page`/`limit` query params and returns the existing `PaginationResponse` envelope (`core/schemas.py`), via `core/pagination.py`'s offset-based `paginate()` — not the cursor-based `paginate_cursor()`, even though both already existed unused.
**Why offset, not cursor, for this specific endpoint:** three independent reasons, not a coin flip. (1) `paginate_cursor` is documented as being for "large, append-heavy result sets" (its own module docstring) — an org's membership list is a bounded admin roster (headcount-sized, rarely changes), the opposite shape. (2) `paginate_cursor` hardcodes newest-first ordering with no ascending option; this endpoint's existing contract is "oldest first" (founding/longest-tenured members surface first) — using it would have silently reversed that. `paginate()` doesn't impose its own ordering, so the existing `.order_by(created_at.asc())` survives untouched. (3) `paginate()`'s output shape already matched the pre-existing `PaginationMeta`/`PaginationResponse` schemas (page/limit/total/total_pages/has_next/has_previous) with zero new schema needed; `paginate_cursor` returns a different, cursor-shaped result with no matching schema anywhere yet, and no page numbers — suited to infinite-scroll UI, not an admin table. `paginate_cursor` is the right tool for something genuinely large and append-only later, e.g. `GET /audit-log` in M3.
**Also fixed alongside this:** an initial attempt at this endpoint's pagination (`get_org_memberships`) called `paginate_cursor` without importing it and discarded its return value, referencing an undefined `result` on the next line — would have raised `NameError` on every call. Caught before commit, never reached a real environment.
**Also fixed the same day:** `decode_refresh_token` (`auth/jwt_handler.py`) now wraps its `TokenPayload` construction in the same `try/except (KeyError, ValueError, TypeError) → TokenInvalidException` pattern `decode_access_token` already used — a malformed refresh-token payload previously raised a raw, unhandled `KeyError` (unstructured 500). New test coverage for the invite-reactivation branch (re-inviting a deactivated member reactivates the same membership row, doesn't duplicate it, restores login).
**Impact:** `tenancy_identity/repository.py`, `service.py`, `router.py` (pagination wiring), `auth/jwt_handler.py`, `tests/memberships/test_memberships.py` (two existing tests updated for the new response envelope, one new reactivation test). 74 tests passing, no schema drift.

**Decision:** `audit_log`/`notifications` tables, RLS policies, `log_action()`/`notify()` (the internal services every later module calls into), and all four endpoints (`GET /audit-log`, `GET /notifications`, `POST /notifications/{id}/read`, `POST /notifications/read-all`) are built and merged into `m3-audit-notifications`. `GET /audit-log` is gated to `hr_administrator`/`business_executive` via `require_org_role` — `05_API_DESIGN.md` never specified who could call it. ## 2026-09-20 — M3 merged to `main`; M4 employee-offboarding gap resolved: offboarding deactivates the linked `Membership`
**Decision:** M3 backend merged to `main` via PR #5. `m3-audit-notifications` deleted (local + remote); `m4-org-structure` branched off the updated `main`. **Why automatic, not manual/optional:** matches how real enterprise identity/HR systems handle this — Okta Lifecycle Management, Azure AD entitlement management, and Workday's leaver workflows all deprovision access automatically the moment HR marks someone terminated in the system of record, specifically because a forgotten manual step here means a former employee keeps working access (dashboards, notifications, everything) indefinitely. That's the actual failure mode this needs to prevent, not a nice-to-have.
**Why this doesn't contradict the 2026-09-07 "block, don't cascade" decision for deleting a referenced department/position:** that decision protects against a delete silently destroying or orphaning other active things — the safe default there is blocking. Offboarding is the opposite shape: ending access *is the intended outcome* of the action, not a side effect to guard against, so cascading automatically is the correct behavior here, not an exception to that principle.
**Mechanical shape:** offboarding is a dedicated action, `POST /employees/{id}/offboard`, not a generic `PATCH employees.status`. In one transaction it sets `employees.status = 'inactive'`, sets the linked `Membership.deactivated_at` if one exists, and logs both to `audit_log` (M3, now available). A dedicated endpoint rather than a generic status PATCH matches how membership deactivation itself is already treated as a deliberate action with consequences (`08_DECISIONS.md` 2026-09-18), not an incidental field edit.
**What this does not resolve:** the other M4 gap in `09_PROGRESS.md` — what happens to an offboarded manager's direct reports (`employees.manager_id` orphaning) — is still open, a separate question not implied by this decision.
**Impact:** `09_PROGRESS.md` M4 entry updated — this question closed, the direct-reports question still open. `01_REQUIREMENTS.md`/`04_DATABASE.md`/`05_API_DESIGN.md` to reflect `POST /employees/{id}/offboard` when M4's actual schema/endpoints are drafted, not yet written since M4 hasn't started building.

## 2026-09-20 — Orphaned-direct-reports gap resolved: offboarding doesn't block, and gets a reinstate action
**Decision:** Offboarding a manager does not block on their having direct reports (`employees.manager_id`) — reports simply keep pointing at the now-inactive manager until someone reassigns them; no forced-reassignment prompt, no auto-reassignment, in MVP. Offboarding also gets a mirror action, `POST /employees/{id}/reinstate`, which sets `employees.status = 'active'` and un-deactivates the linked `Membership` (`deactivated_at = NULL`) if one exists — reusing the exact reactivation mechanism M2 already built for re-inviting a previously-deactivated teammate (`08_DECISIONS.md` 2026-09-17: flip the state back on the same row, don't duplicate it).
**Why:** raised directly — a termination is not always final in the real world (wrongful termination, a suspension reversed, a rehire), so the offboarding design needs to support reversal as a first-class case, not just the one-way "person is gone" assumption the earlier blocking approach implied.
**Why not blocking (unlike deleting a Position):** offboarding is a soft, reversible status change, not a deletion — the `Employee` row still exists, so `manager_id` never actually becomes a dangling/broken foreign key the way a hard-deleted row would leave one. There's nothing for a block to protect against structurally; it would only exist to force an immediate reassignment decision that the business doesn't require and that reinstatement would just undo anyway if the offboarding gets reversed.
**Does not change the 2026-09-07 "block, don't cascade" rule for deleting a Position that's still referenced (`positions.reports_to_position_id`).** That's a genuinely different case — deleting a `Position` row is a real, irreversible hard delete, unlike an employee's `status` flag — and stays blocked, unchanged by this entry. Worth keeping the two separate: employee offboarding (soft, reversible, this decision) vs. position deletion (hard, destructive, 2026-09-07's rule) are not the same operation even though both touch a "who reports to whom" relationship.
**What this leaves genuinely unaddressed, deliberately, as MVP scope:** downstream behavior of a direct report "reporting to" an inactive manager (task assignment, approvals, KPI rollups) is not M4's problem to solve — those are M10/M11/M12 concerns once those modules exist. M4 only needs to not destroy data or force an artificial blocking decision here.
**Impact:** `09_PROGRESS.md` M4 entry — direct-reports gap closed. `05_API_DESIGN.md` to add `POST /employees/{id}/reinstate` alongside `/offboard` when M4's endpoints are drafted.
