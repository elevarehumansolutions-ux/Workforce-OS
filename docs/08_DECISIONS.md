## 2026-09-02 — Backend framework: FastAPI, not Django
**Decision:** FastAPI, SQLAlchemy, Alembic, Celery — same stack as Elevare's existing recruitment platform.
**Why:** Emmanuel has current, recent production FastAPI experience (multiple prior projects) and would need to refresh Django. The recruitment platform already runs FastAPI + SQLAlchemy + Alembic + Celery + asyncpg in production, with real incidents already debugged there (Celery worker OOM, Alembic multiple-heads) — meaning the usual "Django ships faster, batteries included" argument doesn't hold when the alternative isn't a blank slate. Django's admin-panel advantage is also weaker here since the product ships a dedicated React frontend, not Django's HTML admin as product UI (SQLAdmin, built on the same SQLAlchemy models, covers the internal-ops-console use case reasonably well instead). Django's async ORM is also a `sync_to_async` shim over a synchronous driver, not real non-blocking I/O like SQLAlchemy `AsyncSession` + `asyncpg` — a real (if not urgent-for-MVP) difference for later features like cross-platform recruitment integration and concurrent AI calls.
**Impact:** `00_PROJECT_CONTEXT.md` tech stack table updated. Sole backend engineer now maintains one stack across both Elevare products.

## 2026-09-04 — Multi-tenancy: shared schema, shared database, enforced by Row-Level Security
**Decision:** One Postgres database, one set of tables, every table carries a `NOT NULL organization_id`, isolation enforced at two independent layers: application-level authorization (role/permission checks within a tenant) and Postgres Row-Level Security policies (the tenant boundary itself, enforced by the database regardless of what the application queries for).
**Alternatives considered:**
- Schema-per-tenant (separate Postgres schema per customer) — rejected. Migrations run once per schema instead of once total, connection pooling (PgBouncer transaction mode) doesn't play well with per-request `search_path` switching, and cross-tenant analytics get much harder. A worse position on both axes than shared-schema, not a genuine middle ground.
- Database-per-tenant — rejected as the MVP default, kept as a future option. Strongest isolation, but highest operational cost (migrations, backups, and monitoring all multiply per tenant). This is the right answer for a specific enterprise contract that demands dedicated infrastructure (data residency law, noisy-neighbor elimination, independent audit/backup, or simply a procurement requirement), not for every customer by default. Real-world parallel: MongoDB Atlas sells exactly this spectrum as Shared vs. Dedicated cluster tiers.
**Why RLS specifically, not just application-level filtering:** application authorization checks ("is this user allowed to see this resource") remain necessary and are not replaced by RLS — they solve a different problem (in-tenant permissions, e.g. a Manager in one department shouldn't see another department's payroll even though it's the same organization). RLS solves the one thing application code can't be trusted to always get right: a `SELECT` that forgets its `WHERE organization_id = ...` clause, a raw script, a rushed admin tool, a future engineer unfamiliar with the convention. Postgres enforces the tenant boundary as an invisible policy on every query regardless of what the application asked for. This is the standard defense against IDOR-style cross-tenant leaks (Broken Access Control topped OWASP's 2021 Top 10), which is the single most common way multi-tenant SaaS actually gets breached in practice.
**Implementation notes:**
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` plus a policy checking `organization_id = current_setting('app.current_org_id')::uuid` on every tenant-scoped table.
- The current tenant is set once per request via `SET LOCAL app.current_org_id = ...`, inside a transaction, in a single FastAPI dependency, not scattered through the codebase. `SET LOCAL` (not plain `SET`) matters because pooled connections (PgBouncer) are reused across different tenants' requests — a session-scoped setting could otherwise leak between them.
- Elevare's own cross-tenant admin/analytics queries (e.g. billing status across customers) go through a separate, tightly controlled DB role permitted to bypass RLS — not the same connection path application requests use.
**Impact:** `00_PROJECT_CONTEXT.md` tech stack table updated from "leaning" to decided. This is now safe to build against in the database/system design pass.

## 2026-09-04 — Generic Workflow Template/Step model designed, closes the long-standing "Workflow Management" design gap
**Decision:** Workflows (the "Workflow & Departmental Interdependency" MVP feature, §6) are built as a fully generic engine, never as anything specific to Elevare's own process. Elevare's lead-intake process is just the first real data entered into the same tool every customer gets, not a feature built for Elevare specifically.
**Model:** WorkflowTemplate (name + ordered steps) → WorkflowStep (department, default turnaround time, position, optional default assignee) → WorkflowInstance (one running case) → Task (auto-created per active step, inherits deadline, completion triggers the next step). A department can appear more than once in one template. A step's task goes straight to its default assignee if one is set, otherwise lands with that department's manager to delegate. Deadlines are tracked as `due_at` vs `completed_at`; a task open past `due_at` flips to Overdue and notifies before it's even finished, not just after.
**Why this shape, and why it took several passes to land on:** the first drafts conflated things that needed separating, an external tool's data (a CRM) with Workforce OS's own task mechanism, a KPI-measured event (response time, no discrete task needed) with an actual assignable task, and a single hardcoded process with a genuinely reusable engine. Working through Elevare's own recruitment process, then a second, unrelated example (a retail company's complaint-resolution process, different departments, different step count, same engine, no code changes) is what confirmed the model is actually generic and not secretly Elevare-shaped.
**Permission:** template creation/editing is available to HR Administrator (org-wide) or any Manager. A manager building a workflow spanning other departments is expected to have already confirmed realistic turnaround times with those departments, same as they would without any software involved — no formal cross-department approval gate in MVP.
**Status:** Emmanuel proceeded with this model while flagging he doesn't yet have full confidence in every part of it. Revisit and refine once it's visible as an actual schema or screen, rather than treating this as unquestionable.
**Impact:** `01_REQUIREMENTS.md` §6 rewritten with the full model, cross-referenced to §7's weighted KPI scoring (same `due_at`/`completed_at` comparison feeds both).

## 2026-09-07 — Soft-deleting a department/position is blocked, not cascaded, while active references exist
**Decision:** Deleting a department or position fails with a named reason (e.g. "5 active employees still assigned") if it still has active employees, open/in-progress tasks, or a pending AI suggestion attached. No cascading delete, no silent allow.
**Why:** caught in the 2026-09-06 gap review as an undefined rule. Cascading was rejected, it risks quietly wiping or orphaning real employee records. Silently allowing it was rejected too, it would leave active work pointing at something that no longer coherently exists. Blocking with a specific reason is the safer default and doesn't require new cascade machinery.
**What's unaffected:** historical references (a completed task, closed KPI scores) already had this covered by the existing soft-delete convention, nothing changes there.
**Impact:** `01_REQUIREMENTS.md` §2, `04_DATABASE.md` Cluster 2 design notes.

## 2026-09-07 — AI Suggestion generation made idempotent against Celery retries
**Decision:** A partial unique index on `ai_suggestions` (`organization_id`, `suggestion_type`, `position_id`, `department_id`, `kpi_id`, `suggested_department_name`, `WHERE status = 'pending'`), paired with `INSERT ... ON CONFLICT DO NOTHING` in the generation code.
**Why:** caught in the 2026-09-06 gap review. Celery retries failed jobs by default; without this, a retried generation job could create a duplicate pending suggestion for the same target. A database-level constraint was chosen over an application-level check-then-insert because the latter has a race condition under concurrent execution, the database is the only place this guarantee actually holds.
**Impact:** `04_DATABASE.md` Cluster 4, `06_AI_DESIGN.md` new Idempotency section.

## 2026-09-07 — Billing: manual for MVP, Paystack/Flutterwave, automated subscription billing deferred
**Decision:** MVP billing is manual. Elevare invoices a customer directly, they pay via a Paystack or Flutterwave payment link (same providers already assumed for payroll disbursement in `01_REQUIREMENTS.md` §9) or bank transfer, and Elevare staff records it by setting `organizations.subscription_status`/`subscription_expires_at` through the internal admin scripts already designed for the RLS-bypass role. No self-serve checkout, no automated recurring billing, no automated access enforcement based on these fields, all deferred to Phase 2.
**Why:** No SaaS company, regardless of size, builds its own payment processing, PCI compliance and recurring-billing logic (proration, dunning, invoicing) are deep, already-solved problems, always handled through a third-party platform. The open question was timing, not vendor. Most early-stage B2B SaaS companies handle their first cohort of customers manually rather than building automated self-serve billing before there's proven demand for self-serve signup at scale, and this MVP being demoed to investors and pilot customers doesn't change that, a functioning manual process is a normal, expected answer at this stage, not a gap.
**Vendor choice:** Paystack or Flutterwave over Stripe, both are established Nigerian fintechs with real NGN support and existing subscription/recurring-billing APIs for when Phase 2 automation is built; Stripe's direct Nigerian support is inconsistent. Reusing whichever gets picked for payroll disbursement avoids a second third-party integration.
**Impact:** `04_DATABASE.md` Cluster 1, `organizations` gets `subscription_status`/`subscription_expires_at`. Automated billing (self-serve checkout, metering, dunning) logged here as explicit Phase 2 scope, not built now.

**Addendum, same day:** payment history visibility for the customer is a real, separate small addition, not covered by the above. `billing_records` (Cluster 1) is a payment history log, populated manually alongside the fields above, distinct from actual invoice generation, which stays Paystack/Flutterwave's job, not built in-house. `GET /billing/history` (Owner/HR Administrator only) and a matching read-only frontend screen were added for this. ## 2026-09-05 — AI suggestion generation: LLM API call, not a hand-curated rules table (technical implementation choice, does not need Jennifer's sign-off)
**Decision:** Critical-role and revenue-allocation suggestions are generated by calling an LLM (Claude/GPT/Azure OpenAI, provider TBD) with the org's existing department/position/industry context, not by matching against a hand-written table of title patterns per industry.
**Why the original "rules-based" framing needed revisiting:** `01_REQUIREMENTS.md` §8 confirms, as an actual product requirement from Jennifer, "AI suggests, human approves, nothing auto-activates." It does not require any specific implementation technique. "Rules/template-based, not ML" was Emmanuel's own technical framing underneath that requirement, chosen because training a custom ML model needs a proprietary dataset that doesn't exist. That framing missed a third option: calling an already-trained LLM via API needs no dataset at all, and avoids the real practical problem a hand-curated rules table would have created, someone, most likely Jennifer, would have had to author and maintain title-matching patterns for every industry this product might ever sell into. ## 2026-09-17 — Live app DB role fixed: `elevare` (superuser) was being used for real traffic, RLS was never actually enforced
**Decision:** The live app (FastAPI, Celery worker, Celery Beat) now connects as `elevare_app`, a newly-provisioned ordinary Postgres role with no `SUPERUSER`/`BYPASSRLS` attributes (`backend/scripts/db/provision_app_role.sql`). `DATABASE_URL` points at it. **What was actually wrong:** `docker-compose.yml`'s `POSTGRES_USER: elevare` makes `elevare` a Postgres superuser — that part is correct and unavoidable, every fresh Postgres cluster requires exactly one superuser at `initdb` time, regardless of what it's named. Superusers (and any role with `BYPASSRLS`) skip RLS checks entirely, so every RLS policy documented since 2026-09-04 was installed correctly and syntactically fine, but had never actually been enforced against a real application request — for the whole of M1 and the portion of M2 leading up to this fix. Every earlier "proof" RLS was working was actually the app's own `WHERE` clauses happening to filter correctly, not Postgres enforcing anything.
**How it was caught:** a new test (`test_patch_membership_not_found_across_orgs`) returned 200 instead of the expected 404 — cross-org access that should have been invisible under RLS was succeeding. Confirmed via direct `pg_roles`/`pg_tables` queries that the app's own connection had `rolsuper=t`.
**Follow-on bug this exposed:** see next entry — `INSERT ... RETURNING` requires the read (`USING`) policy too, not just `WITH CHECK`. This only started failing once the app stopped running as a role that bypassed the check entirely.
**Impact:** `app/core/config.py` gets `migration_database_url`; `.env`/`.env.example` split `DATABASE_URL`/`MIGRATION_DATABASE_URL`; `alembic/env.py` uses the migration credential. `docs/RLS_POLICIES_EXPLAINED.md` §2 and `07_SECURITY.md`'s new provisioning checklist explain this for future reference. `docker-compose.yml` itself required no change — the fix is which credential each process is handed, not the container topology.

## 2026-09-17 — `INSERT ... RETURNING` needs the read policy satisfied too, not just the write policy
**Decision:** `OrganizationRepository.create_organization` now generates the new org's `id` in Python (`uuid.uuid4()`) before constructing the `Organization` object, and sets `app.current_org_id` to that exact id before the `INSERT` runs — rather than adding a `USING` exception to the `organizations` RLS policy.
**Why:** once the app stopped running as a superuser (previous entry), registration started failing with "new row violates row-level security policy for table organizations" even though `WITH CHECK`'s bootstrap branch should have allowed the insert. Root cause: the ORM's `flush()`/`refresh()` always issues `INSERT ... RETURNING` to read back server-generated columns (`created_at`); Postgres requires a `RETURNING`ed row to also satisfy the table's `USING` (read) policy, not just `WITH CHECK` — confirmed directly via `psql` as `elevare_app` (insert succeeds without `RETURNING`, fails with it). `organizations`' `USING` clause deliberately has no bootstrap exception (giving it one would mean any request that forgets to set org context could read every organization's row) — so establishing the real org context before the insert, rather than relaxing the read policy, closes the gap without reopening that hole.
**Correction to a prior claim:** this fix initially failed a different way — reading `new_organization.id` immediately after `Organization(**organization)` returned `None`/unset. `BaseModel.id`'s Python-side `default=uuid.uuid4` is only invoked at `flush()`, not at object construction, contrary to what had been assumed/stated earlier in this project. Fixed by generating the id explicitly before constructing the object.
**Impact:** `tenancy_identity/repository.py`'s `OrganizationRepository.create_organization`. `docs/RLS_POLICIES_EXPLAINED.md` §8 documents the general `RETURNING`-vs-`USING` mechanism for future tables that hit the same pattern.

## 2026-09-18 — Membership deactivation scoped per-org, and two deeper bugs it uncovered by actually testing the fix
**Decision:** `PATCH /memberships/{id}` with `is_deactivated=True` now sets a new `Membership.deactivated_at` (nullable timestamp), not `User.account_status`. Deactivating someone from one organization no longer locks them out of every organization they belong to — `User.account_status` stays what it was, untouched by this endpoint. `get_current_membership` (`core/dependencies.py`) and `refresh()` now reject a deactivated membership the same way a missing one is rejected. `login()` filters to active (non-deactivated) memberships when picking which org to log into, and re-inviting a previously-deactivated person reactivates their existing row instead of failing on the unique constraint or creating a duplicate.
**Why scoped, not global:** raised as a direct question, confirmed by the user — a person in two unrelated organizations (a consultant invited into a client's org, say) must not have Org A's HR Administrator able to lock them out of Org B. `User.account_status` is deliberately global (2026-09-13's "sole account-state field" decision) for account-level concerns (banned, suspended platform-wide); membership-level access needed its own, separate flag.
**Two real, pre-existing bugs surfaced only by writing a real cross-org test and running it, not by reading the code:**
1. **`login()` never established real org context before relying on eager-loaded organization data.** It only "worked" in the existing test suite because the test environment's shared connection/transaction happened to leave a matching `app.current_org_id` behind from an earlier step (registration) in the same test. On a genuinely fresh connection (production), `organizations`' own RLS policy (no bootstrap-read exception at the time) would have silently returned no organization at all. 2. **`organizations`' RLS policy had no bootstrap-read exception at all**, meaning `GET /me` could never actually return organization details for more than one membership — RLS only ever allows seeing one org's row at a time otherwise. Read-only exception — `WITH CHECK` (writes) is unchanged.
3. **Both `login()` and `get_me()` now explicitly clear `app.current_org_id` before their own bootstrap logic runs**, rather than assuming it was never set. **A new exception, `NoActiveMembershipException` (403), replaces reusing the generic `InternalServerErrorException` (500)** for "this user has zero active memberships anywhere" at login — deactivation makes this a normal, reachable outcome now, not the anomalous edge case (a brand-new user with literally zero memberships ever) the original 500 was written for.

## 2026-09-18 — `GET /memberships` paginated with `paginate()` (offset), not `paginate_cursor()`
**Decision:** `GET /memberships` now takes `page`/`limit` query params and returns the existing `PaginationResponse` envelope (`core/schemas.py`), via `core/pagination.py`'s offset-based `paginate()` — not the cursor-based `paginate_cursor()`, even though both already existed unused.
**Why offset, not cursor, for this specific endpoint:** three independent reasons, not a coin flip. (1) `paginate_cursor` is documented as being for "large, append-heavy result sets" (its own module docstring) — an org's membership list is a bounded admin roster (headcount-sized, rarely changes), the opposite shape. (2) `paginate_cursor` hardcodes newest-first ordering with no ascending option; this endpoint's existing contract is "oldest first" (founding/longest-tenured members surface first) — using it would have silently reversed that. `paginate()` doesn't impose its own ordering, so the existing `.order_by(created_at.asc())` survives untouched. (3) `paginate()`'s output shape already matched the pre-existing `PaginationMeta`/`PaginationResponse` schemas (page/limit/total/total_pages/has_next/has_previous) with zero new schema needed; `paginate_cursor` returns a different, cursor-shaped result with no matching schema anywhere yet, and no page numbers — suited to infinite-scroll UI, not an admin table. `paginate_cursor` is the right tool for something genuinely large and append-only later, e.g. `GET /audit-log` in M3.
**Also fixed alongside this:** an initial attempt at this endpoint's pagination (`get_org_memberships`) called `paginate_cursor` without importing it and discarded its return value, referencing an undefined `result` on the next line — would have raised `NameError` on every call. Caught before commit, never reached a real environment.
**Also fixed the same day:** `decode_refresh_token` (`auth/jwt_handler.py`) now wraps its `TokenPayload` construction in the same `try/except (KeyError, ValueError, TypeError) → TokenInvalidException` pattern `decode_access_token` already used — a malformed refresh-token payload previously raised a raw, unhandled `KeyError` (unstructured 500). New test coverage for the invite-reactivation branch (re-inviting a deactivated member reactivates the same membership row, doesn't duplicate it, restores login).
**Impact:** `tenancy_identity/repository.py`, `service.py`, `router.py` (pagination wiring), `auth/jwt_handler.py`, `tests/memberships/test_memberships.py` (two existing tests updated for the new response envelope, one new reactivation test). 74 tests passing, no schema drift.

**Decision:** `audit_log`/`notifications` tables, RLS policies, `log_action()`/`notify()` (the internal services every later module calls into), and all four endpoints (`GET /audit-log`, `GET /notifications`, `POST /notifications/{id}/read`, `POST /notifications/read-all`) are built and merged into `m3-audit-notifications`. `GET /audit-log` is gated to `hr_administrator`/`business_executive` via `require_org_role` — `05_API_DESIGN.md` never specified who could call it. ## 2026-09-21 — Real bug found and fixed: `alembic/env.py` never imported the model registry, making `alembic revision --autogenerate` silently destructive
**What happened:** generating M6's migration the normal way (`alembic revision --autogenerate -m "..."`, exactly what `make migration` runs) produced a migration whose `upgrade()` did not create `okrs`/`key_results` at all — instead it **dropped nearly every other table in the schema** (`organizations`, `users`, `memberships`, `departments`, `positions`, `employees`, `business_dna`, `audit_log`, `notifications`, everything). Autogenerate correctly compared "what the (empty) models say should exist" against "what the live database actually has," and the live database losing was the outcome — it doesn't know the emptiness was a bug, not real intent to delete everything.

No entry in this log documents which. What matters going forward: the bug is real, reproducible on demand (confirmed by regenerating after the fix and getting a correct, minimal diff), and would have hit M7 onward regardless of whether M2–M5 happened to dodge it.
**Fix:** `alembic/env.py` now imports `app.core.model_registry` (side-effect import, same `# noqa: F401` pattern `main.py` already uses) before reading `Base.metadata`. Verified by deleting the broken migration (never applied to any database), regenerating, confirming the new diff only adds `okrs`/`key_results` and their indexes with no drops anywhere, then applying it and confirming via direct `psql`/`pg_policies` queries that both tables and their RLS policies exist exactly as intended.
**Why this matters beyond M6:** every future milestone (M7 onward) runs `alembic revision --autogenerate` the same way M6 just did — without this fix, each one would have silently regenerated the same schema-destroying diff, relying on someone catching it by inspection every single time rather than the tooling being safe by construction. This is now fixed at the source.
**Impact:** `alembic/env.py`. No schema/model changes. ## 2026-09-22 — M7 (AI Suggestions) pre-build decision: rejected suggestions suppressed until the next Quarterly Objective Review
**Decision:** once HR explicitly rejects an `ai_suggestions` row, the same suggestion (same target, same `suggestion_type`) is suppressed from regenerating until the next Quarterly Objective Review fires for that org — not permanently, and not on a fixed time-based cooldown (e.g. 60/90 days).
**Why tied to the quarterly cycle instead of a fixed duration:** the system already has two regeneration triggers — event-driven (an org-structure/OKR change) and the Quarterly Objective Review (`01_REQUIREMENTS.md` §4/workflow #4, `organizations.fiscal_year_start_month`-driven). A fixed day-count cooldown would be a third, independent time period with no relationship to either trigger, able to lapse at an arbitrary point mid-quarter for no particular reason. Suppressing until the next Quarterly Review reuses a period the system already treats as meaningful — rejection holds for the rest of the current quarter, and gets a fresh chance to be re-evaluated exactly when the system next re-examines the org's strategy anyway, not on some unrelated clock.
**What this rules out:** permanent suppression was also considered and rejected — a suggestion rejected once under one set of conditions could legitimately become correct again after a real change (a department's revenue allocation shifts, a role's criticality changes), and permanent suppression would hide that from HR indefinitely with no path back.
**Shapes the implementation:** the suppression check needs the rejected row's timestamp and the org's current fiscal-quarter boundary (derived from `organizations.fiscal_year_start_month`, same field M2 already shipped for the Quarterly Review job itself) to determine whether a matching rejected suggestion falls inside or outside the current quarter — not just a static "already rejected, skip" flag. This needs to be designed into the idempotency logic alongside the existing pending-duplicate index (`08_DECISIONS.md` 2026-09-07), not bolted on after.
**Impact:** `10_CURRENT_TASK.md`'s M7 entry — the "needs a decision" gap is now resolved. No code changes yet; this decision is the input the M7 generation/idempotency design starts from.

## 2026-09-22 — Task Blocking & Escalation added, Jennifer's submission after reviewing early screens
**Decision:** `task_blocks` (`04_DATABASE.md` Cluster 6, `01_REQUIREMENTS.md` §6a): an assignee can mark a task blocked (reason + category: `awaiting_approval`/`awaiting_other_department`/`external_dependency`/`other`), which suppresses that task's Overdue flag and excludes it from lateness scoring while blocked. Goes through the same `pending`/`approved`/`rejected` review lifecycle already used for `ai_suggestions` and membership deactivation, reviewed by the assignee's manager or an HR Administrator.
**Origin:** Jennifer described a scenario, an employee blamed for a late task when the real cause was upstream (a delayed approval, another department not delivering on time), and asked for an "avenue" for the employee to explain, reviewed by "the upper team." She separately suggested the KPI impact should "reduce" rather than land immediately, and Emmanuel proposed a Celery Beat trigger prompting an explanation when a task expires, plus an AI-generated incident narrative for HR/Executive.
**Sharpened from the original description, and why:**
- **One table, not two.** A "block" (Emmanuel's ServiceNow/Jira-style pause suggestion, made during this same discussion) and an "escalation" (Jennifer's explain-and-review ask) aren't different features, the act of marking a task blocked *is* the escalation; the review that follows is what judges it. `task_blocks` serves both the proactive case (blocked before going overdue, `unblocked_at` still null) and the reactive case (a task went overdue with no block recorded, the existing Overdue Celery Beat scan prompts for one after the fact).
- **`due_at` is never mutated.** "Currently overdue" and "actually late for scoring" both become derived calculations that exclude approved blocked duration, consistent with `due_at` being written once at task creation and never rewritten (same principle already applied to `kpi_scores` immutability).
- **Grounded in established precedent, not invented from scratch:** Google SRE's "blameless postmortem" practice (separating what happened from individual blame surfaces real process failures instead of burying them) is the reasoning for why this is worth building at all, not just a fairness feature; Jira Service Management/ServiceNow's SLA-pause pattern is the direct precedent for the block mechanism itself.
**KPI effect, confirmed by Emmanuel:** a `pending` block holds that task out of scoring entirely until reviewed (not scored provisionally and corrected later, which would conflict with closed-period `kpi_scores` being permanent history). `approved` excludes the blocked duration from lateness; `rejected` scores it as if never blocked.
**AI narrative:** reuses the shared LLM-calling utility already built for AI Suggestions/Executive Summaries, a new content type, not a new integration, reading `task_blocks`' structured data (department, category, duration, outcome) to distinguish systemic patterns from genuine individual underperformance.
**Explicitly deferred (Phase 2 candidate):** a fully proactive SLA-pause where a workflow step's own clock formally pauses mid-flight, rather than the assignee self-reporting a block, is the more mature version of this same idea, but requires redesigning how `workflow_steps` turnaround/deadline computation works. The self-reported block is the right MVP scope.
**Milestone placement:** folded into **M10 (Task)** for the mechanism itself and **M12 (Performance)** for the scoring integration and AI narrative, not a new milestone, both were unstarted when this was decided, and each piece belongs with the milestone that already owns that concern.
**Impact:** `01_REQUIREMENTS.md` new §6a, `04_DATABASE.md` Cluster 6 gets `task_blocks`, `09_PROGRESS.md` M10 and M12 updated, Trello M10/M11/M4 frontend cards updated same day with the related UI actions this and the 2026-09-18 review surfaced.

**Known limitations, considered and accepted, not oversights (2026-09-23):**
- **Reactive-block timing is inherently imprecise.** When a block is recorded *after* `due_at` already passed (the Overdue Celery Beat's after-the-fact prompt), there's no way to verify how much of the delay was a genuine external wait versus the assignee simply not getting to it, unlike a proactive block, whose timing is confirmed before the outcome is known. The fix considered and rejected: letting the assignee set `blocked_at` to whenever they claim the block actually started. Rejected because that turns a system-recorded timestamp into a user-editable one, breaking the same audit-integrity principle that keeps `due_at` and `kpi_scores` write-once. `blocked_at` stays "when this was recorded," not "when the assignee says it started" — which is what makes proactive-vs-reactive timing itself a free, tamper-proof signal for the reviewer. The imprecision is the accepted cost of that integrity, reviewer judgment carries more weight on a reactive block than a proactive one, by design.
- **Whole-workflow-instance lateness is a related but separate, unsolved question.** `task_blocks` explains why one specific task was late; it says nothing about why an entire multi-step `workflow_instance` ran long overall, since each step already gets a fresh `due_at` once it starts (a late Step 1 doesn't compress Step 2's window, Step 2 just starts later). A workflow can run long in total with every individual step scoring on-time. This is a process-throughput metric, not an individual-fairness one, and nobody (Jennifer or otherwise) has asked for it. Classified **nice-to-have, out of current scope** — not built now, flagged here so a future session doesn't mistake the absence for a bug.

## 2026-09-23 — Real bug found and fixed: the pending-duplicate partial unique index never actually fired, for any suggestion type
**What happened:** while starting the repository layer (the method that inserts a suggestion via `INSERT ... ON CONFLICT DO NOTHING`), checking whether the partial unique index could even be referenced by name in `ON CONFLICT ON CONSTRAINT ...` (it can't — a plain `CREATE UNIQUE INDEX` isn't a named table constraint, confirmed by the error Postgres actually raises) led to testing the correct index-inference form directly against the dev DB. That test — inserting the same `critical_position` target twice inside one transaction — landed **two rows**, not one. The 2026-09-07 index has been silently non-functional since it was first documented, for every suggestion type, not just one.
**Root cause:** every suggestion type in this table only populates one of `position_id`/`department_id`/`suggested_department_name`, leaving the other two columns null on every row. Standard SQL unique-index semantics treat `NULL <> NULL` — a composite unique index never considers two rows a duplicate if any of the compared columns is null on both sides. The original design note's claim ("Postgres treats NULL columns as never conflicting, so this index correctly enforces one pending suggestion per target") had the mechanism backwards: null columns being "never conflicting" is *why* the index fails to catch a duplicate, not why it succeeds.
**Fix:** `NULLS NOT DISTINCT` added to the index (`CREATE UNIQUE INDEX ... NULLS NOT DISTINCT WHERE status = 'pending'`) — a Postgres 15+ feature (this project runs 16) that makes the index treat two nulls in the same column as equal for uniqueness purposes. Verified by dropping and recreating the index with the fix, live, and re-running the exact same duplicate-insert test: the second insert now correctly returns zero rows.
**Why this wasn't caught by the 2026-09-07 decision that introduced the index, or by writing the migration:** the same reason this log has recorded before (2026-09-17 `RETURNING`-vs-`USING`, 2026-09-18 stale RLS test suite, 2026-09-21 `alembic/env.py` autogenerate bug) — a constraint that reads correctly and a constraint that's been proven correct by actually exercising it are different things. Nothing about `04_DATABASE.md`'s SQL block was syntactically wrong; the semantics were just wrong, and SQL semantics around `NULL` are exactly the class of thing that looks obviously fine on a read-through and isn't.
**Caught before it shipped:** this migration hadn't merged or been PR'd yet (built and fixed on `m7-ai-suggestions` in the same session), so it was corrected at the source — the migration file itself — rather than stacked as a follow-up fix, matching how the M6 `alembic/env.py` bug was handled.
**Follow-up gap, also closed same day:** the fixed index only existed as raw SQL in the migration, not declared anywhere in the `AISuggestion` model — meaning the model and the live schema could silently drift, and the next `alembic revision --autogenerate` (M8, adding `kpi_id`) would reflect the DB, find an index no model accounts for, and could propose dropping it. Added as `Index(..., unique=True, postgresql_where=text("status = 'pending'"), postgresql_nulls_not_distinct=True)` in `AISuggestion.__table_args__` — verified to compile to character-identical SQL to what's already live, and `alembic check` now reports "No new upgrade operations detected," confirming model and DB agree.
**Impact:** `backend/alembic/versions/ee15b3a6eb57_add_ai_suggestions_and_ai_usage_log_.py` (index definition + docstring), `backend/app/modules/ai/models.py` (`Index` added to `__table_args__`), `04_DATABASE.md` Cluster 4 (design note corrected, previously stated the opposite of what's true).

## 2026-09-23 — AI service never commits; first service draft reviewed and corrected
**Decision:** `AISuggestionService` (like every other service) does not call `commit()`. The transaction boundary belongs to whoever owns the unit of work — a router for HTTP paths, the Celery task for generation.
**Why this matters more here than elsewhere:** `app.current_org_id` is set transaction-scoped (`set_config(..., true)`), so a `commit()` ends the transaction and wipes the tenant context. Generation calls `create_suggestion_if_eligible` once per candidate in a loop; a per-candidate commit would leave every candidate after the first with no tenant context — RLS then hides the organization row and blocks the insert. Same trap class as the `business_dna` full-rollback bug (2026-09-21). Verified convention: only `ai/service.py`'s first draft committed inside a service; every other module commits in its router.
**Also corrected in the same review** (verified by running, not just reading): the module didn't import (`OrganizationNotFoundException` didn't exist — added); the service called a nonexistent repository method; the create schema had no `position_id`/`department_id` so two of three suggestion types couldn't be expressed; `Decimal` percentage fields were typed `str` (pydantic rejects a `Decimal` into `str`); the response schema lacked `from_attributes` and carried a phantom `reviewed_rationale` field; `datetime.now()` was naive (silently correct only because the app container and DB session are both UTC — the codebase convention is `datetime.now(UTC)`); the duplicate-pending path (`create_pending_suggestion` returning `None`) crashed instead of being a quiet no-op. The create schema now also mirrors the DB CHECK's type-to-target pairing and types risk/criticality with the real enums, so a malformed or LLM-invented candidate fails at the boundary — a raw `IntegrityError` mid-batch would abort the whole Postgres transaction, and a bad enum value would otherwise only surface later when HR approves and it hits the `positions` CHECK.
**Open dependency this surfaces (not built, deliberately):** a Celery task has no request dependency to set `app.current_org_id`, so the generation task must establish tenant context itself before calling the service. Belongs to the event-triggered-task step.
**Impact:** `ai/{service,schemas,repository}.py`, `core/exceptions.py` (`OrganizationNotFoundException`), 17 tests across `tests/ai/`.

## 2026-09-24 — Reviewing a suggestion is one atomic conditional UPDATE, not read-then-write
**Decision:** `AISuggestionRepository.reject_pending_suggestion` is a single `UPDATE ai_suggestions SET status='rejected', reviewed_at=now, reviewed_by_user_id=... WHERE id=:id AND status='pending' RETURNING *`. It returns the row, or `None` if nothing changed. Approve/edit will follow the same shape.
**Why not the house pattern (load, check status, mutate, flush — e.g. `update_okr`):** a check-then-write has a gap between the check and the write. Two HR admins with the same pending suggestion open, one approves (the real position becomes `is_critical = true`), the other — who loaded it earlier — rejects: both saw "pending", both pass the check, both write. Result: the position is critical while the suggestion says "rejected", and the rejection wrongly starts the quarterly suppression clock on something that was actually applied. Same class of problem as the duplicate-pending row (2026-09-07): only the database can close the window, so the pending check is part of the `UPDATE` (Postgres locks the row; the second statement re-evaluates the `WHERE` after the first commits and matches nothing). Applies to approve most of all, since approve also writes onto `positions`/`departments`.
**`None` is deliberately ambiguous at the repository level:** it means either "no such suggestion visible to the caller" (including another org's — RLS hides it from the `UPDATE`) or "already reviewed". Which one is a business distinction (404 vs 409), so the service resolves it with `get_suggestion_by_id`, not the repository.
**`reviewed_at`/`reviewed_by_user_id` are set on rejection** (as decided 2026-09-23) — the quarterly suppression reads `reviewed_at`. `datetime.now(UTC)`, per the codebase convention.
**Status values use `SuggestionStatus` constants throughout the repository** (not string literals), so a typo fails loudly instead of silently never matching.
**Open dependency for the service layer (not built yet):** nothing in `core/exceptions.py` fits "suggestion not found" (404) or "already reviewed" (409) — both need adding. The service also needs an `audit_log` entry per decision (`log_action`, per the `update_okr` pattern).

## 2026-09-24 — Service-level reject built: atomic update first, lookup only on failure
**Decision:** `AISuggestionService.reject_suggestion(suggestion_id, actor_user_id)` tries the atomic `reject_pending_suggestion` first; only if that returns `None` does it call `get_suggestion_by_id` to tell **404** (`SuggestionNotFoundException` — doesn't exist, or another org's, which RLS hides) from **409** (`SuggestionAlreadyReviewedException` — exists but no longer pending). On success it writes an `audit_log` entry (`action="reject"`, `entity_type="ai_suggestion"`, `changes={"old": {"status": "pending"}, "new": {"status": "rejected"}}`) and returns the rejected suggestion.
**Why this order, and why it was corrected in review:** the first draft read the row and checked `status` before writing — the read-then-write gap the atomic UPDATE (same date, above) exists to close. Under a lost race the atomic UPDATE correctly matched nothing and returned `None`, which the draft then passed to `model_validate(None)` — a `ValidationError`, i.e. a 500 for the losing reviewer instead of a clean 409 (verified: pydantic rejects `None` there). Reordering fixes that and saves a query on the success path.
**Cross-org is deliberately a 404, not a 409:** a 409 would tell another organization that the suggestion exists. RLS makes it look like it doesn't (tested).
**The "old" audit value is a known constant, not a snapshot:** the atomic UPDATE only matches pending rows, so the previous status is always `pending` — no snapshot helper needed, and `ai` doesn't reach into `okrs.service`'s private `_snapshot`.
**Audit `organization_id` comes from the row itself** (`suggestion.organization_id`), not a separate parameter, so it can't disagree with the data — same as `update_okr`.
**Impact:** `ai/service.py`, `ai/repository.py`, `core/exceptions.py` (`SuggestionNotFoundException` 404 / `SuggestionAlreadyReviewedException` 409), `tests/ai/test_ai_suggestion_service_review.py` (4 tests: success + audit entry, 404, 409 with no second audit entry, cross-org 404). 28 tests in `tests/ai/`.

## 2026-09-24 — Department names are unique per organization (closes a gap found while building AI approval)
**Decision:** a department's name must be unique within its organization among non-deleted departments, compared on a normalized key (NFKC, trimmed, whitespace collapsed, lowercased). Enforced by a partial unique index — `uq_departments_org_name_active` on (`organization_id`, `name_normalized`) `WHERE deleted_at IS NULL` — over a database-generated `departments.name_normalized` column. `POST /departments` and `PATCH /departments/{id}` return **409** on a duplicate. A deleted department's name can be reused; two organizations can each have "Operations".
**Why (found, not planned):** while designing `missing_department` approval, inspection showed nothing in Org Structure prevented duplicate names at all — no constraint, no service check — so a double-click, or approving an AI-suggested name HR had since created by hand, produced two "Customer Success" departments. A completeness gap in M4 independent of AI (`CLAUDE.md`'s production standard names duplicates/races), classified required-for-completeness, built as its own slice on the user's go-ahead. It also protects the AI approval path for free: approving a `missing_department` whose name now exists fails with a 409, the request's transaction rolls back, and the suggestion returns to `pending` for HR to reject.
**Design choices, and the alternatives rejected:**
- **Per organization, not global.** A global unique on `name` would stop two customers both having "Operations", and the conflict itself would reveal that another tenant uses a name (a cross-tenant information leak that RLS can't hide, since uniqueness is checked across all rows).
- **`WHERE deleted_at IS NULL`** — soft-deleted departments must not block reuse of their name.
- **Normalized key via generated column**, same reasoning as `ai_suggestions` (2026-09-23): "Ops" / "ops " / a non-breaking-space variant must count as one name; the database derives it, so no write path can forget it.
- **Failure is mapped from `IntegrityError` to 409, not `INSERT ... ON CONFLICT DO NOTHING`.** `ON CONFLICT DO NOTHING` is right where a duplicate is an *expected harmless no-op* (a retried AI suggestion job). Here a duplicate is a *user error to report*; `DO NOTHING` would swallow the reason and hand back `None` to reinterpret, and `UPDATE` (rename) has no `ON CONFLICT` at all. One mechanism covers create and rename, matching the existing `register()` duplicate-email pattern. The error is matched by the violated index's *name* (`_is_duplicate_department_name`), so an unrelated constraint failure can never be mislabelled "duplicate". The write runs inside a SAVEPOINT (`begin_nested`) so the rejected statement doesn't abort the surrounding transaction or wipe `app.current_org_id` (same trap as the `business_dna` upsert, 2026-09-21). A first attempt at this in the repository used `ON CONFLICT DO NOTHING` on the generic `sqlalchemy.insert` with no matching unique index (would have raised `AttributeError` on every department create, verified) — replaced, repository restored to its committed state.
**Migration `61454952170a` (new, on top of the AI migration):** adds the column and index. Existing data may contain duplicates the index would refuse to build over, so before creating it the migration renames any duplicate among non-deleted departments — oldest keeps its name, newer ones get " (2)", " (3)" — preserving every row (verified against seeded duplicates in the dev DB; `alembic check` clean; downgrade/upgrade round-trips; renames are not reversed on downgrade). **Deployment note:** this rewrites duplicate display names in any environment it runs against (including the VPS demo) — cosmetic, but worth knowing before the next deploy.
**Also done:** `normalized_name_expr` moved from `ai/models.py` to `app/core/text.py` — Org Structure importing it from the AI module would have inverted the documented dependency direction (Org sits underneath AI). Pure move, AI tests unchanged.
**Not built, classified nice-to-have:** the same gap exists for `locations.name` and `positions.title` (per department) — nothing prevents duplicates there either. Less clear-cut than departments (two identical position titles in a department can be legitimate), so left for a product call, not done unasked.
**Impact:** `app/core/text.py` (new), `organization/{models,service}.py`, `ai/{models,repository}.py` (import), migration `61454952170a`, `tests/organization/test_department_uniqueness.py` (7 tests: duplicate, variants, session survives a rejected create, cross-org allowed, reuse after delete, rename conflict leaves the name unchanged, own-name recapitalization allowed). `04_DATABASE.md` Cluster 2, `05_API_DESIGN.md` departments line updated.

## 2026-09-24 — Edit action designed (agreed with the user; not yet built)
**What HR can change, per suggestion type:** `critical_position` → `criticality_type` and/or `risk_level` (never *which* position); `revenue_allocation` → the percentage; `missing_department` → the name. Anything not supplied defaults to the AI's value, so HR can tweak one field. The suggestion becomes `edited`, `reviewed_*` holds HR's values (defaults copied from `suggested_*`), and the same `_apply_reviewed_values` write-through used by approve applies them (extracted 2026-09-24 once three types made it a rule-of-three).
**Rejected, at the boundary:** (1) a field that doesn't apply to the suggestion's type (a percentage on a position suggestion); (2) an edit with no fields at all; (3) an edit whose supplied values all equal the AI's — that is an approve, not an edit. (3) matters beyond tidiness: `04_DATABASE.md`/`06_AI_DESIGN.md` keep `suggested_*` vs `reviewed_*` as the training-data pair ("AI proposed X, human corrected it to Y"); an `edited` row with no actual correction would pollute that signal.
**Shape:** because applicability needs the suggestion's type, the service reads the row first (404 if not visible), validates the edit against the type, then does the atomic `UPDATE ... WHERE status='pending'` (a `None` result is then unambiguously a 409). This deliberately differs from reject/approve's "claim first, look up on failure": a suggestion's type is immutable, so the pre-read can't race — only `status` can change, and the atomic UPDATE still guards it. Values not supplied use `COALESCE(<HR value>, suggested_*)` inside the UPDATE, the same "copy inside the statement" idea as approve.

## 2026-09-24 — Edit repository method built; found and fixed an ORM session-synchronization trap in all three atomic review updates
**Built:** `AISuggestionRepository.edit_pending_suggestion` — atomic `UPDATE ... WHERE status='pending'` setting `reviewed_*` to the reviewer's value if supplied, else the AI's (`COALESCE`), status `edited`. Keyword-only arguments so a percentage can't be mistaken for a name. 5 tests.
**Bug found by a failing test (not by review):** a cross-org edit attempt correctly matched no database row (RLS), yet a suggestion object the session already held read `edited` — SQLAlchemy's default `synchronize_session` evaluates the `WHERE` in Python against in-memory objects and applies the `SET` to them even when the database matched nothing. The database was never wrong; the session's in-memory picture was. The identical trap existed in `reject_pending_suggestion` and `approve_pending_suggestion`; their tests passed only because they didn't keep the object alive (the identity map holds weak references).
**Fix, at the source, for all three:** `.execution_options(synchronize_session=False, populate_existing=True)` via one shared, commented constant — stop the Python-side guess, and let a *returned* row refresh the in-memory object. A regression test holds a suggestion object, fires all three review actions from another org, and asserts the object is untouched.
**Also caught:** a stray trailing comma (`.returning(...),`) made the statement a one-item tuple; missing `decimal`/`func` imports. Both fixed.

## 2026-09-24 — Decided (reverses `05_API_DESIGN.md`): approve and edit are two endpoints, and the strict edit rules stand
**Decision (user's call, option B):** `POST /ai-suggestions/{id}/approve` takes no body and approves as proposed; `POST /ai-suggestions/{id}/edit` takes only the fields being changed. `05_API_DESIGN.md` had settled a *single* `approve` endpoint with an optional override body, where the server compared the body against `suggested_*` and chose `approved` vs `edited`. ## 2026-09-29 — KPI deletion handled via a group-level reconciliation endpoint, not a bare `DELETE`

**Gap found:** `05_API_DESIGN.md`'s Performance section never documented a delete endpoint for KPIs at all (`POST|GET /kpis`, `PATCH /kpis/{id}`, the two `/scores` endpoints only). `09_PROGRESS.md`'s M8 completeness gap (flagged 2026-09-18 — "the same validation needs to re-check the remaining KPIs after one is deleted") assumes a delete endpoint exists to attach that check to; it didn't.

**Decision:** rather than add a bare `DELETE /kpis/{id}` and duplicate the weight-sum check across three separate endpoints, a single group-level endpoint is added: **`PUT /departments/{department_id}/kpis`** (optional `location_id` query param, selecting the department-wide group vs. a location-scoped one — `organization_id` is never a request field, it comes from the authenticated tenant context like everywhere else in this API). The request body is the *entire* desired KPI list for that group; the backend reconciles it against current state in one transaction:
- an item with an `id` → update (only the supplied fields change);
- an item with no `id` → create;
- an existing KPI whose `id` is **not** present anywhere in the submitted list → delete.

The submitted list's weights are validated to sum to exactly 100 before anything commits, matching the existing "409 on drift" convention, using the standard `ErrorResponse` envelope already used everywhere in this API (`code: "KPI_WEIGHT_MISMATCH"`), with the computed total included in `message` (e.g. `"KPI weights for this department must total 100%. The submitted list totals 90%."`) so the frontend can render a specific, actionable toast rather than a generic failure. On success, the response returns the full resulting list with real database ids for newly-created KPIs — no follow-up `GET` required for the frontend to know what it just saved.

**Why one endpoint instead of a bare delete:** removing a KPI from a weighted group is never really a standalone action — the remaining KPIs almost always need their weights adjusted in the same motion, or the group is left invalid. Exposing "delete" and "rebalance the rest" as two separate calls creates a window where the group doesn't sum to 100, and a failure partway through (dropped connection, a second person editing concurrently) can leave it stuck there. A single call that reconciles creates, updates, and deletes together either fully succeeds or fully fails, with no partial state possible — the same principle modern weighted-goal products (Workday, SuccessFactors, Lattice-style goal-weighting screens) apply by treating the department's whole KPI set, not individual rows, as the unit of change.

**What stays unchanged:** `POST /kpis` and `PATCH /kpis/{id}` remain as already documented, for the ordinary single-KPI case (e.g. renaming a KPI, changing its `key_result_id`) — both already validate the group sum on their own per the existing "enforce on create and edit" rule; nothing about that changes here. `DELETE /kpis/{id}` is deliberately **not** added — every deletion goes through the group endpoint instead, so the weight-sum check only has to live in one place, not three.

**Worth flagging to Uche, not yet confirmed with him:** the KPI setup step of the onboarding wizard (M8 frontend scope) is a natural fit for this same group endpoint — building out a department's KPI list from scratch is the same "send the whole desired list" shape as editing an existing one, just against an empty starting group. Whether his screen actually calls it that way (versus repeated `POST /kpis` calls during initial setup) is a frontend implementation choice, not dictated here, but the endpoint is available either way — flagged on the matching Trello card so it isn't missed.

**Impact:** `05_API_DESIGN.md` Performance section gets the new endpoint documented. `09_PROGRESS.md` M8's completeness-gap note updated to point at this resolution. `10_CURRENT_TASK.md` backend scope bullet updated to reference the resolved mechanism instead of describing it as an open gap.

## 2026-09-29 — `kpi_scores` becomes a running, updatable figure during the quarter, not a single quarter-end entry

**Gap found:** as originally designed, `POST /kpis/{id}/scores` recorded a period's `actual_value` exactly once, understood to happen after the quarter had already ended. For any KPI whose actual value isn't automatically counted by something else already in the system (a real revenue figure, not a task count), that meant nobody — not even an HR Administrator or Business Executive — could see any progress at all while the quarter was still running. Only the final number, only after the fact. For a product whose core premise is performance *visibility*, not a quarterly report card, that's a real gap, not a nice-to-have.

**Decision:** `POST /kpis/{id}/scores` becomes an upsert against the current, still-open period. `hr_administrator` **and** `business_executive` (not `hr_administrator`-only, unlike most of this module's other mutations) can call it as many times as they want while the quarter is running — each call updates that KPI's `actual_value` for the current period and recalculates `score_percentage`, so the figure keeps catching up to reality as new real-world numbers come in (e.g. checking the bank balance again next week), instead of sitting blank until the last day.

**Why this doesn't contradict the existing "permanent history" rule (04_DATABASE.md, `kpi_scores` has no `deleted_at`):** that rule was always about a period that has already *ended*. Nothing changes there — once `period_end` has passed, the row locks, and any correction is still a new period's row, never an edit to the old one. The only change is *before* that date: while the current quarter hasn't closed yet, the same row can be revised repeatedly. The rule now applies precisely from the moment `period_end` passes, not from the moment the row is first created.

**Impact:** `05_API_DESIGN.md`'s `POST /kpis/{id}/scores` line updated to describe the upsert behavior and the two-role write access. `10_CURRENT_TASK.md`'s `kpi_scores` bullet updated to match. `04_DATABASE.md`'s design note on `kpi_scores` narrowed to state explicitly that "permanent, no `deleted_at`" applies once `period_end` has passed, not before.

## 2026-09-30 — KPI progress tracking split into two modes: automatic (task count) and manual (typed-in figure); new `kpis.tracking_mode` field

**Decision:** a KPI's mid-quarter progress is tracked one of two ways, chosen when the KPI is defined:
- **`task_count`** — for a KPI whose target is literally a count of things happening (e.g. "close 20 deals"). Progress is a live count of completed tasks linked to that KPI (`tasks.kpi_id`) within the current period, computed on read — nobody enters anything, no stored running value needed.
- **`manual`** (the default) — for a KPI whose target is a real-world figure nothing in this app can see on its own (revenue, average response time, a rate). Progress is whatever `hr_administrator`/`business_executive` last entered via `POST /kpis/{id}/scores` for the current, still-open period (the 2026-09-29 upsert decision above) — updatable as often as they like, but still a person typing in a number, not automatic.

New column: `kpis.tracking_mode` (`TEXT NOT NULL DEFAULT 'manual' CHECK (tracking_mode IN ('manual', 'task_count'))`), set at KPI creation, editable like any other KPI field.

**Why not just infer this from whether the KPI happens to have tasks linked to it:** a task can be linked to a KPI for reasons that have nothing to do with counting toward its target — e.g. a "call the client to invoice them" task tied to a revenue KPI doesn't mean +1 revenue per task completed. Only an explicit choice, made by whoever defines the KPI, is safe here; guessing risks silently treating a manual KPI's task count as if it means something it doesn't.

**Real dependency, not a decision being ducked:** the actual live-count query (`task_count` mode) needs the `tasks` table, which doesn't exist yet — Task is M10, sequenced after M8/M9. So this milestone (M8) only adds the `tracking_mode` column, defaulted to `manual` (the one mode that can actually work before M10 lands). The live-count read itself is M10/M12's job, once `tasks.kpi_id` is real — settling the column now means that later work builds against an already-fixed field instead of needing its own schema change.

**Impact:** `04_DATABASE.md` Cluster 5's `kpis` table gets `tracking_mode`, with a design note. `05_API_DESIGN.md` Performance section notes the future `task_count` live-progress read (M10/M12, not yet built) alongside the manual upsert that already works today. `09_PROGRESS.md` M8 and M10/M12 entries cross-reference this. `10_CURRENT_TASK.md` M8 backend scope updated to include the new column.

## 2026-09-30 — `task_count` KPIs close out via a scheduled snapshot job, reusing the Quarterly Objective Review's shape and the manual-mode upsert

**Decision:** when a `task_count`-tracking KPI's quarter ends, its final progress number is written into `kpi_scores` by a scheduled job, not a person. The job runs off the same fiscal-quarter-boundary check the Quarterly Objective Review already does (`core/fiscal.py`, the org's `fiscal_year_start_month`), and for every `task_count` KPI whose quarter just closed, does the live task-count one last time and upserts it into `kpi_scores` using the exact same upsert mechanic already decided for `manual` mode (08_DECISIONS.md 2026-09-29) — same table, same one-row-per-KPI-per-period shape, same "locked once `period_end` passes" rule afterward. The only two differences from `manual` mode: what triggers the write (the scheduler, not a person calling `POST /kpis/{id}/scores`) and where the number comes from (a live count of completed tasks linked to the KPI, not a typed-in figure).

**Why this shape, not something new:** this is the standard pattern real systems use to freeze a live number into permanent history at a period boundary — accounting's month-end close, a CRM's quarterly quota snapshot, an analytics tool's daily rollup. All work the same way: a scheduled job runs right at the boundary, reads the current live value, writes it down once. This app already built a job with exactly that shape for a different reason (the Quarterly Objective Review, M7) — reusing it means no new scheduling infrastructure and no new date-boundary logic, just one more per-org, per-KPI step added to a job that already runs at the right moment.

**Must be idempotent, the same lesson the Quarterly Review job already learned:** the close job can retry or run slightly late, so it has to be safe to run more than once for the same KPI/period without creating a duplicate or conflicting row — the same reason `manual` mode's `POST /kpis/{id}/scores` is an upsert rather than a plain insert. Both paths converge on one upsert operation; only the caller and the data source differ.

**Status:** design decided, not yet built — it depends on M10 (`tasks`) existing before there's anything to count, and naturally lands as M12 work (Scoring, Dashboards) alongside the rest of `kpi_scores`' automated writes.

**Impact:** `09_PROGRESS.md` M10/M12 entries updated to reference this. `05_API_DESIGN.md`'s `task_count` "not yet built" note updated to mention the close job. `10_CURRENT_TASK.md` unaffected — this is M10/M12 scope, M8 only shipped the `tracking_mode` column.

## 2026-10-02 — Email normalization, and reactivation split out of invites

**Email normalization (required for completeness, found while building grant-login):** emails were stored and compared as typed, so `Chidi@x.com` and `chidi@x.com` were different accounts, and an invite to one never matched a user registered as the other. **Decision:** one canonical form, trimmed and lower-cased, enforced at three layers so no single slip can reintroduce the problem — (1) a shared `NormalizedEmail` type (`core/schemas.py`) on every client-supplied email: register, login, resend-verification, forgot-password, invite, and employee `work_email` (previously a bare `str`, so it is now also validated as an email); (2) the user and pending-invite lookups normalize their input too; (3) `CHECK (email = lower(btrim(email)))` on `users.email`, `invites.email` and `employees.work_email`, so even a write that bypasses the schemas fails. The existing `UNIQUE` on `users.email` therefore becomes case-insensitive uniqueness with no extra index. Migration `1f55b227d9d9` lower-cases existing rows; if two existing users differ only by case it **stops and lists them** instead of choosing one, and it retires all but the newest of any duplicate pending invites. Tested against deliberately messy data, not only a clean DB.

**Reactivation is no longer a side effect of inviting:** `invite_teammate` used to silently reactivate a deactivated member and overwrite their role. That mixed two concerns and let an invite restore access with no checks or audit. **Decision:** inviting a deactivated member is a **409** `MEMBERSHIP_DEACTIVATED`; `POST /memberships/{id}/reactivate` (optional `role`, omit to keep the old one) is the one way back. It is audit-logged and refuses someone whose employee record is offboarded, pointing to `POST /employees/{id}/reinstate`, so login access and employment status can't disagree. `grant-login` inherits the rule (a deactivated member is refused, not revived). `reinstate_employee` is unchanged.

**`PATCH /memberships/{id}` stops reactivating (decided later the same day, after the question was answered):** `is_deactivated` accepts only `true`; `false` is a 422 pointing at `/reactivate`. It was left alone at first because Uche's Team Management might already call it; the answer was that it can stop. Implemented in the *request schema*, not in `MembershipService.update_membership`, because `reinstate_employee` legitimately calls that service method with `False`. **Audit gap closed the same day:** `POST /memberships` and `PATCH /memberships/{id}` previously wrote no audit entries; they now do (`invite` without the token, `add`, `update`, `deactivate`, `reactivate`, each with old/new state).

**M9 step 1 — `organizations.timezone` (same day):** the attendance auto-close needs "midnight for this org", and no timezone existed anywhere. **Decision:** `organizations.timezone`, `VARCHAR(64) NOT NULL DEFAULT 'Africa/Lagos'` (migration `8bff259ac5fb`; existing orgs filled in by the database default), stored as an IANA *name* rather than an offset so daylight saving works for a future non-Nigerian customer. **Set through `PUT /business-dna`** next to `organization_name` (option A, chosen over a separate `PATCH /organization`: one more field on an endpoint the onboarding wizard already calls, no new screen), validated against `zoneinfo.available_timezones()` (exact spelling; no database CHECK since Postgres has no zone list that stays in step with Python's). An explicit `null` is ignored. Because `organization_name` was never in the Business DNA audit entry, both org-level fields now appear in it under `organization_name`/`organization_timezone` keys with old and new values. **`zoneinfo` needs timezone data on the machine:** `tzdata` (2026.4, already present only transitively) is now pinned explicitly in `requirements.txt`, so a different base image or a slimmer dependency tree can't silently break validation or the auto-close job. **`GET /business-dna` stays a 404 until the first `PUT`** — kept as is (see `09_PROGRESS.md` M9 for the reasoning).

**M9 attendance built (same day, everything except the nightly auto-close job):** `attendance_records` (migration `83927f74b4eb`, RLS, one-open-record partial unique index, three CHECKs), repository, service, router, 23 service/repository tests + 8 HTTP tests. Decisions made while building, beyond the design already recorded above:
- **Clock-in is `INSERT ... ON CONFLICT DO NOTHING` on the one-open-record index**, not look-then-insert with a SAVEPOINT. The insert itself says whether this call created the row, so a repeat tap and a lost race are the same code path; the response carries `already_clocked_in` so the widget can say the right thing. (Same pattern as `create_pending_suggestion`; the conflict target must match the partial index exactly, as the `kpi_weight` bug showed.)
- **Clock-out is *not* idempotent:** no open record -> `409 NOT_CLOCKED_IN`. It is one atomic conditional `UPDATE ... WHERE clock_out_at IS NULL`, so two simultaneous clock-outs can't both succeed and the first clock-out time stands. The same `close_open_record` will serve the nightly auto-close (`closed_by = system`). `clock_out_at` is clamped to `GREATEST(requested, clock_in_at)` so a slightly slow client clock never produces negative hours.
- **History visibility:** own history by default; `hr_administrator` and `business_executive` may read any employee in their org via `employee_id`; everyone else gets 403. Date filters are calendar days in the **organization's timezone**, end inclusive.
- **No separate "currently clocked in" endpoint:** newest record with `clock_out_at: null`.
- **Nightly auto-close, built the same day** (migration `774346b5b100`, `attendance/tasks.py`, Beat entry `attendance-auto-close`). Decisions: (1) **cutoff = the organization's most recent local midnight**, applied to *every* open record that clocked in before it ("any record before today", not "exactly yesterday"), so a missed run just closes more next time and a rerun closes nothing. Records from today are untouched. (2) **Hourly, not nightly**: each org's midnight is a different UTC hour; only orgs that currently have an open record are enqueued. (3) **Two tasks**, the M7 shape: a scan task finds the orgs, then one task per org closes under that org's RLS context, so one org failing or retrying never holds up the rest. (4) **The cross-tenant question is a second narrow `SECURITY DEFINER` function**, `organizations_with_open_attendance()` returning only org id + timezone; the app role still has neither `BYPASSRLS` nor superuser (verified, and asserted in a test). Now recorded in `07_SECURITY.md`. (5) **Audit entry per record** (`auto_close`, `actor_user_id` null = system). (6) **In-app notification, category `system`, to the employee and to their manager** (skipping anyone without a login, never the same person twice); no email, as decided. (7) A real clock-out is never overwritten: the close is a conditional `UPDATE ... WHERE clock_out_at IS NULL`. **Deploy note:** the Celery worker and beat containers must be restarted to pick up the new task and schedule (same as the 2026-09-27 `include=[]` fix).

**`invite_status` on every employee response (same day, a "Pending invite" badge was judged sensible):** `"pending"` while an unaccepted invite sent from the employee's row still works, `"expired"` once it lapsed, `null` when none is waiting or the employee already has a login. Computed rather than stored: one query per response batch against `invites` (which carries `employee_id` and `is_used`; a resend marks the old invite used, so there is at most one unused invite per employee). Present on all eight employee endpoints so a client merging responses never loses the badge.

**Impact:** `05_API_DESIGN.md`, `09_PROGRESS.md` updated. Tests: `tests/authentication/test_email_normalization.py` (6), `tests/memberships/test_membership_reactivation.py` (5), the old invite-reactivation test rewritten to assert the refusal plus the new endpoint.

## 2026-10-06 — Frontend/backend domain split (Vercel + api.workforceos.online); a real deploy-automation bug found doing it

**Decision:** `workforceos.online` (the apex) now points at the Vercel-hosted frontend; the backend moved to `api.workforceos.online`. DNS: a new `A` record for `api`, same VPS IP, DNS-only/unproxied — same reasoning as the original domain setup (`08_DECISIONS.md` 2026-09-22), Cloudflare's proxy would otherwise intercept Caddy's ACME HTTP-01 challenge. `Caddyfile` updated to serve `api.workforceos.online` instead of the bare domain.

**Bug found doing it: the automated deploy job never actually restarted `caddy`, so the new domain never took effect on its own.** `docker-compose.prod.yml`'s `caddy` service uses a plain `image:` (no `build:` key) with `Caddyfile` bind-mounted in read-only. The deploy script ran `docker compose up -d --build` — `--build` only rebuilds services that have their own `build:` key (`api`, `celery_worker`, `celery_beat`); it does nothing for `caddy`, and Compose has no way to detect that a bind-mounted file's *content* changed, so the already-running `caddy` container was left untouched, still serving the old config. Confirmed live: `https://api.workforceos.online/health` failed with a raw SSL handshake error (`curl` exit 35 — no TLS listener recognized that hostname at all) until `docker compose up -d --force-recreate caddy` was run by hand, at which point Caddy's logs showed it only *then* starting to request a certificate for the new domain.

**Fix:** `.github/workflows/ci-cd.yml`'s deploy step now runs `docker compose up -d --build --force-recreate` — `--force-recreate` added so every deploy recreates every container regardless of whether Compose thinks its image/config changed, closing the gap for any future config-only change (not just `Caddyfile`) on a service without its own `build:` key. Negligible cost at this stack's size (five tiny containers); correctness over the marginal efficiency of skipping a recreate Compose wasn't sure it needed anyway.

**Why this matters beyond this one incident:** this is the same class of gap as the `alembic/env.py` autogenerate bug (2026-09-21) and the `ENVIRONMENT=production` crash loop (2026-09-22) — something that looked right in the deploy script and had worked for every prior deploy (because every prior change happened to touch an image-rebuilt service), caught only because this specific change didn't fit that pattern. Found by actually curling the new domain after a real deploy, not by reading the workflow file.

**Follow-up still needed, not yet done:** `backend/.env`'s `CORS_ALLOWED_ORIGINS`/`APP_URL` still need the real Vercel URL (currently placeholders, per the 2026-09-22 follow-up checklist in `11_DEPLOYMENT.md`) — tracked there, not repeated here.

**Impact:** `Caddyfile`, `.github/workflows/ci-cd.yml`. No app code changed.

## 2026-10-06 — "Department manager" = a nullable `departments.head_employee_id`, one named person per department

**Gap being closed:** M10's overdue scan notifies "the assignee and the department manager" and M11 routes a workflow task with no assignee to "that department's manager", but nothing modelled who that is (no column on `departments`, no manager table). "Manager" already meant two other things: the membership *role* `manager`, and a person's *reporting manager* (`employees.manager_id`).

**Decision (the user's requirement: "one specific person that HR names for each department"; my recommendation accepted):** add `departments.head_employee_id`, a nullable foreign key to `employees`. HR sets it. No new Manager table or class.

**Rules:**
1. **Optional.** A department can exist without a head. It is normally set *after* the department is created: during onboarding, Setup Organization comes before any employee exists, so the head is picked later, on the department's edit screen (or from an employee's page).
2. **Any active employee of the same organization.** Not required to belong to that department (real heads sometimes sit one level up). One person may head several departments.
3. **If the head is offboarded,** the field is cleared in the same transaction and HR administrators are notified, so it never points at someone who left. Reinstating does not restore it.
4. **If a department has no head,** anything that would notify or route to "the department manager" goes to the organization's HR administrators instead of nowhere.
5. Every change is audit-logged (old and new head).

**Considered and rejected:** an `is_manager` flag on employees (can be true for none or several people in a department, can't say which department, adds a fourth meaning of "manager", and employees have no department of their own to put a uniqueness rule on); deriving it from the `manager` role (none or several again); using only `employees.manager_id` (a task with no assignee has nobody whose manager to look up).

**Kept as a later upgrade:** `departments.head_position_id` (the head follows the *position*, so a successor is automatically the head), consistent with how criticality attaches to positions, not people. Not chosen now because the model doesn't enforce one holder per position. Switching later is one migration; M10/M11 only ever ask "who is this department's head?", so nothing built on this is wasted.

**Built 2026-10-06 on branch `m4-followups`** (migration `34c5feaf5535`; 12 tests in `tests/organization/test_department_head.py`; the "no head, so alert HR" fallback is deliberately left for M10, where the alert is sent). What was listed as to-do: migration, `PATCH /departments/{id}` accepts `head_employee_id` (validated: exists, active, same org) or a dedicated assign action, clearing on `offboard_employee`, HR notification, audit entry, `DepartmentResponse` returns it, tests, `04_DATABASE.md` Cluster 2. Frontend (Uche): a "Department head" picker on the department edit screen and the head shown in the department list; a Trello card is written when the backend lands (`CLAUDE.md`, "Frontend impact").

## 2026-10-07 — `positions.reports_to_position_id` is validated: same organization, not itself, no loops

**Gap being closed:** the field was accepted on `POST|PATCH /positions` with no validation. A position could report to itself, two positions could form a ring, or one could point at another organization's position (the database's foreign key doesn't consult row-level security, so it accepts any existing id). Found 2026-10-04 while testing the Setup Organization page's mocked "Reporting Hierarchy".

**Decision / what was built (`PositionService._validate_reports_to`):**
1. **Parent must exist in this org** (404 `POSITION_NOT_FOUND`, message "The position it should report to was not found"). No separate "organization ids must match" comparison: the existing `get_position_by_id` is RLS-scoped and ignores deleted rows, so another org's position is simply not found; a comparison would be unreachable code.
2. **A position cannot report to itself** (422). Only checkable on update: a new position has no id yet.
3. **No loops** (422): walk up from the proposed parent through its own `reports_to_position_id`; if the position being edited appears, it would become its own boss. A visited set and a depth cap (`_MAX_HIERARCHY_DEPTH = 100`) mean an old ring elsewhere in the data ends the walk instead of hanging it.
4. Runs only when `reports_to_position_id` is in the payload and not null, so `null` and unrelated edits are never revalidated. A parent in a different department is allowed.

**Error codes:** 404 for a missing parent follows the existing pattern for ids inside a request body (department head, user link); self and loop are 422.

**Accepted, not built:** two simultaneous requests (`A to B` and `B to A`) could each pass and together make a ring; closing that needs row locking, out of proportion for HR editing an org chart. A `GET /positions/hierarchy` tree endpoint (the frontend can build the tree from `GET /positions`).

**Impact:** `05_API_DESIGN.md`, `09_PROGRESS.md` (M4). Tests: `tests/organization/test_position_hierarchy.py` (8). Full suite 520 passing.
