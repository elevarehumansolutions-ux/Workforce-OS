# AI Design

Consolidates decisions already made across `01_REQUIREMENTS.md` §8, `08_DECISIONS.md` (2026-09-05), and `04_DATABASE.md` Cluster 4/`02_SYSTEM_DESIGN.md`'s AI Suggestions module into one place.

## Core principle (product requirement, not negotiable by implementation)

AI is a recommendation layer, never an autonomous decision-maker. Every suggestion goes through the same pending → approved/edited/rejected lifecycle in `ai_suggestions`. Nothing it proposes ever takes effect on `positions`, `departments`, or `kpis` until a human explicitly approves it, possibly with corrections.

## Implementation: LLM API call, not a hand-curated rules table

Suggestions are generated by calling an LLM with the org's existing context, **Claude, decided 2026-09-07.** This was a revision, not the original plan, see `08_DECISIONS.md` 2026-09-05: a rules table would have required someone, most likely Jennifer, to hand-author critical-role patterns per industry, not a reasonable ask, and unnecessary since a pre-trained LLM needs no such dataset.

## Cost and usage tracking

Every LLM call, both suggestion generation and the periodic executive summary, is metered: token counts and estimated cost written to `ai_usage_log` (`04_DATABASE.md`) through a shared internal LLM-calling utility, not duplicated per-feature. An org's own HR Administrator can see their own organization's usage via `GET /ai-usage`, ordinary RLS applies. Aggregate cost across every customer, for Elevare's own margin/cost tracking, goes through the same internal admin scripts already built for billing (`07_SECURITY.md`), not a new access path.

## The four suggestion types

Matches `ai_suggestions.suggestion_type`:

| Type | LLM is given | LLM may propose |
|---|---|---|
| `critical_position` | existing departments already flagged critical, and their existing positions | which existing `position_id` to flag critical, plus `criticality_type`/`risk_level` |
| `revenue_allocation` | an existing critical department, `business_dna` context (industry, revenue drivers) | a `revenue_allocation_percentage` for that `department_id` |
| `missing_department` | the org's existing department list, its OKRs | a department **name** that doesn't exist yet, `suggested_department_name` |
| `kpi_weight` | a department's existing KPI set | a `weight` split across them, summing toward 100 |

## AI is restricted to entities that already exist

For `critical_position`, `revenue_allocation`, and `kpi_weight`, the LLM must select from IDs given to it in the prompt, department, position, and KPI records that are already real rows, never invent one. This is enforced in code, not just prompted for: the response is validated against the actual IDs sent, a hallucinated ID is a rejected generation, not a suggestion that reaches the review queue. `missing_department` is the one deliberate exception, its entire point is naming something that doesn't exist yet, that suggestion creates a name string, never a department row directly, HR still has to explicitly accept it before any row is created.

## Debounce

Repeatedly triggering the same generation (e.g. toggling a department's critical flag on and off) has no cost control without one. A short Redis-backed cooldown fixes this cheaply, reusing infrastructure already in place rather than adding a new one: `SET ai_suggestions:debounce:{organization_id} 1 NX EX 60` before enqueueing. If the key already exists (`NX` fails), skip enqueueing, a recent trigger already covers it. If it succeeds, proceed and let the key expire naturally after 60 seconds. This bounds real LLM API cost from rapid repeated triggers without meaningfully delaying the genuine, single-trigger case.

## Idempotency

Celery retries a failed job by default. Without protection, a retried generation task could create a second, duplicate pending suggestion for the same target. `ai_suggestions` has a partial unique index (`04_DATABASE.md`) enforcing one pending suggestion per organization/type/target, and the generation code uses `INSERT ... ON CONFLICT DO NOTHING`, so a retry is a safe no-op, not a duplicate.

## Trigger and execution

Event-triggered Celery task, not scheduled (see `03_ARCHITECTURE.md` Background Jobs). Fired by Org Structure's service (after a department is marked critical, or a position added to one) or OKR's service (after a new objective is saved), calling `ai_suggestions_service.request_suggestions(...)`. Runs as a background job so an LLM call's latency, a second or more, never blocks the save operation that triggered it.

## Review and the training-data flywheel

`reviewed_*` columns mirror every `suggested_*` column, populated on both plain approval and edit, so "AI proposed X, human decided Y" is always a complete pair, never requiring a branch on `status` to know which column to trust. This exists because `01_REQUIREMENTS.md` §8 confirms approvals/corrections become future training data, once enough organizations have gone through the loop, this table is the raw material for eventually training a proprietary model, which is the actual reason the LLM-call approach was chosen over a rules table that would generate nothing worth learning from.

## Not built for MVP

Anything beyond the four suggestion types above, workforce insight generation, workload/productivity pattern detection, succession recommendations, is explicitly Phase 2/3 per `01_REQUIREMENTS.md` §8. No proprietary dataset or infrastructure for it should be built ahead of that need.
