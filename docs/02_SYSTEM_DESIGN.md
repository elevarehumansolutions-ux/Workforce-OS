# System Design

Built directly on `04_DATABASE.md` — every table from that document is owned by exactly one module below. See `08_DECISIONS.md` for the reasoning trail behind each boundary; this doc is the resulting structure.

## Shape

Modular monolith: one deployable FastAPI application, internally split into modules. No microservices, no separate databases per module, chosen for a 2-person team (see `08_DECISIONS.md`, multi-tenancy decision). Boundaries are drawn so that extracting a module into its own service later, if that's ever actually needed, is a mechanical change, not a redesign.

## The one rule

**A module may only call another module through its service layer. Never by importing another module's repository, models, or writing a query against a table it doesn't own.**

This is the single rule the whole structure depends on. It's what prevents the failure mode that motivated this whole exercise: the same piece of logic (a validation rule, a status calculation) re-implemented slightly differently in a dozen unrelated places, because nothing stopped anyone from reaching directly into a table from anywhere in the codebase. If every write and read to a table goes through that table's owning module's service, there is exactly one place that logic can live.

Each module follows the same internal shape:
```
module_name/
  __init__.py
  models.py       # SQLAlchemy models for the tables this module owns
  repository.py   # raw DB operations — the only file that queries this module's tables
  service.py      # application logic — the only entry point other modules are allowed to call
  router.py       # API endpoints
```

## Modules

### Identity
**Owns:** `organizations`, `users`, `memberships`
**Responsibility:** who is logged in, which company, what role. Signup, login, tenant boundary.
**Depends on:** nothing — this is the foundation everything else sits on.
**Called by:** every other module, for permission checks (does this membership's role allow this action).
**Why one module, not three:** none of the three tables mean anything useful without the other two — a `User` with no `Membership` can't do anything in this product. Splitting them would turn the single most common operation in the app, "who is this, what can they do", into a three-module orchestration for zero benefit. See `08_DECISIONS.md`, 2026-09-04/05.

### Org Structure
**Owns:** `locations`, `departments`, `positions`, `employees`
**Responsibility:** the shape of a specific company — its offices, departments, job roles, and the people filling them.
**Depends on:** Identity (permission checks — who's allowed to edit org structure).
**Called by:** OKR, AI Suggestions, Performance, Task, Workflow, Attendance — all of them reference a department, position, employee, or location.
**Why separate from Identity:** `employees.user_id` is nullable — a person can be a fully real employee, with a position and a manager, before ever being invited to log in. That's HR/business data, not auth data, a different concern from Identity's job.
**Why `locations` didn't earn its own module:** it's just a name and an address, with no independent complexity or growth path, unlike `employees`, which already carries real distinct data and will carry a lot more once Phase 2 (payroll, leave) lands.

### Business DNA
**Owns:** `business_dna`, `business_dna_core_values`
**Responsibility:** the company's identity, captured once during onboarding — vision, mission, industry, capital investment.
**Depends on:** Identity (permission check — HR Administrator only).
**Called by:** Performance (reads `capital_investment_amount` to compute department revenue targets).
**Why separate from OKR:** no foreign key connects `business_dna` to `okrs` at all. They're related only at the application-logic level (the revenue-target math reads from both), not at the data level, and they have different lifecycles — Business DNA is edited rarely, OKRs are a continuously growing list.

### OKR
**Owns:** `okrs`, `key_results`
**Responsibility:** corporate and departmental objectives and their key results.
**Depends on:** Identity (permission), Org Structure (`department_id`).
**Called by:** Performance (`key_result_id` on `kpis`).
**Why "additive, never clears" needed no special design:** adding an objective mid-quarter is just inserting a new row. Existing ones are untouched by default — the requirement falls out of the schema for free.

### AI Suggestions
**Owns:** `ai_suggestions`
**Responsibility:** generates and tracks the review lifecycle (pending/approved/edited/rejected) for AI-proposed critical positions, revenue allocations, missing departments, and KPI weight splits. Suggestions are generated by calling an LLM with the org's existing context, not a hand-curated rules table (see `08_DECISIONS.md`, 2026-09-05) — this module owns the LLM call itself.
**Depends on:** Identity (permission, `reviewed_by_user_id`), Org Structure (reads department/position data to build the LLM's context; writes an approved `critical_position`/`revenue_allocation`/`missing_department` suggestion back through Org Structure's service, never by writing to `positions`/`departments` directly), Performance (same pattern for `kpi_weight` suggestions — reads existing KPIs for context, writes an approved weight back through Performance's service).
**Why its own module:** no foreign key ties `ai_suggestions` to `business_dna` or `okrs` at all — it reaches into Org Structure and Performance for its subject matter, but its actual job, running the suggest/review lifecycle, is a distinct, generic concern that will keep growing (it's explicitly the mechanism `01_REQUIREMENTS.md` §8 relies on to eventually produce training data for a real model).

### Performance
**Owns:** `kpis`, `kpi_scores`, `employee_kpi_scores`, `executive_summaries` (added 2026-09-07)
**Responsibility:** KPI definitions, weighting, and period-by-period scoring; the quarterly revenue-target math (`departments.revenue_allocation_percentage` × `business_dna.capital_investment_amount`, divided by quarter).
**Depends on:** Identity (permission), Org Structure (`department_id`, `location_id`), OKR (`key_result_id`, nullable), Business DNA (`capital_investment_amount`).
**Called by:** Task (a task linked to a KPI inherits that KPI's weight — Task's service calls Performance's service to fetch it), AI Suggestions (`kpi_weight` suggestions read/write through here).
**Why its own module, not folded into OKR or Org Structure:** it answers a genuinely different question, not "what are we trying to achieve" or "what does the company look like," but "how well is it actually going, measured." It also already carries real, growing complexity — the weighted scoring curve, quarterly trends — that neither of the other two modules has.

### Task
**Owns:** `tasks`
**Responsibility:** the assignable unit of work, standalone or generated by a workflow step.
**Depends on:** Identity (permission), Org Structure (`department_id`, `assigned_to_employee_id`), Performance (`kpi_id` weight lookup), Attendance (checks whether the assignee has clocked in today before returning their task list — §5, task list only appears after clock-in).
**Called by:** Workflow (creates a task when a step becomes active or completes — through Task's service, never a direct insert into `tasks`).
**Why separate from Workflow:** a standalone task, `workflow_instance_id` and `workflow_step_id` both null, has complete, meaningful existence with zero workflow involved. That's what earns it a boundary of its own rather than being absorbed into Workflow.

### Workflow
**Owns:** `workflow_templates`, `workflow_steps`, `workflow_instances`
**Responsibility:** the reusable engine — a named, ordered sequence of steps, each with a department, a default turnaround, an optional default assignee — that runs a case from start to finish, creating the next step's task when the current one completes.
**Depends on:** Identity (permission — HR Administrator or any Manager), Org Structure (`department_id` on templates and steps, `default_assignee_employee_id`), Task (calls `task_service.create_task(...)` whenever a step becomes active — never writes to `tasks` directly).
**Called by:** nothing — no other module depends on Workflow.
**Why this direction and not the reverse:** the logic that decides "a new task is needed now" is a workflow concern (which step is next, what's its turnaround), but the table that stores tasks belongs to Task. Workflow calling into Task's service, rather than Task knowing anything about Workflow, is what keeps Task's rules (how `due_at` gets computed, what a valid status is) in exactly one place regardless of who's asking for a task to be created.

### Attendance
**Owns:** `attendance_records`
**Responsibility:** plain clock-in/clock-out tracking.
**Depends on:** Identity (permission), Org Structure (`employee_id`).
**Called by:** Task (the clock-in check described above).
**Why it earns a module despite being one small table:** unlike `locations`, it has real, already-planned future weight — once Payroll returns in Phase 2, it has to read attendance to calculate deductions and adjustments. That's a concrete growth path, not a speculative one.

### Notifications
**Owns:** `notifications`
**Responsibility:** per-user notification stream, filterable by category.
**Depends on:** Identity (`recipient_user_id`).
**Called by:** every domain module — AI Suggestions (new suggestion ready for review), Workflow (approval request), Task (overdue alert), and any future module that needs to reach a person.
**Why it's a different kind of module than the rest:** every other module represents a real business concept — an org chart, an objective, a task. Notifications doesn't, it's shared infrastructure, the same category as a logging or email-sending service would be. The dependency arrow only ever points *into* it, never out of it, it has no knowledge of what a Task or a Workflow is, it just receives "notify this user" from whoever needs it.

### Audit Log
**Owns:** `audit_log`
**Responsibility:** records who changed what, when, across every other module, added to MVP scope 2026-09-06.
**Depends on:** Identity (`actor_user_id`).
**Called by:** every domain module, on every mutating action, the same one-directional shape as Notifications.
**Why added, and why now rather than later:** enterprise HR software is expected to answer "who approved this KPI weight" or "who changed this employee's critical status." Unlike a deferrable feature, this can't be retrofitted after the fact, a write that happened before the audit call existed has no history to recover. Cheapest to build in from day one, alongside the modules it will log, rather than added once eight modules already have uninstrumented write paths.
**Why its own module and not folded into Identity:** it needs `actor_user_id` from Identity, but its job, recording events from every other module, is structurally identical to Notifications' job, receive from everyone, know about no one. Same category of infrastructure module, not a business-domain concept.

## Dependency direction, summarized

```
Identity  ←—  everything (permission checks)
Notifications  ←—  everything (calls in, never calls out)
Audit Log  ←—  everything (calls in, never calls out)

Org Structure  ←—  OKR, AI Suggestions, Performance, Task, Workflow, Attendance

Business DNA  ←—  Performance
OKR           ←—  Performance
Performance   ←—  Task, AI Suggestions
Attendance    ←—  Task
Task          ←—  Workflow
```

Nothing depends on Workflow. Nothing depends on Notifications' internals (only calls into it). Identity and Org Structure sit underneath almost everything, by design, they're the two modules every other module needs to answer "who is this" and "where do they fit."
